## 5. Symptom / proximate / root cause
- Symptom: Trust T1_scan_stale/T1_odom_stale bursts (ages 0.59–0.79 s, 2–4 ticks).
- Proximate: FAST-LIO main thread starved in the runqueue 0.4–0.7 s (no output), then in-order backlog drain in FAST-LIO and level_bridge
  (RELIABLE depth 100/20) extends staleness by 1–2 ticks. HAL lidar is on time in the cleanest burst (#5); trust ingress/eval are not involved.
- Root cause (evidence-backed for 5/5 bursts): a new DDS participant joining domain 0 (our tools, ros2 CLI, any node) triggers a
  discovery storm (60–110 runnable threads, host idle <10 %) on an already saturated 8-core host; FAST-LIO, confined to 2 CPUs shared
  with the vendor /em/algo cpuset, cannot migrate and is starved. Contribution of the pinning vs. pure host saturation = HYPOTHESIS
  (strong: bridge/trust, unpinned, were delayed only secondarily), not yet A/B-tested.
- Secondary finding: during burst #4 HAL emitted one lidar cloud with header.stamp = 0 → FAST-LIO buffer clear + bridge pose-cache clear.
  Needs separate tracking (vendor HAL behaviour under load).
