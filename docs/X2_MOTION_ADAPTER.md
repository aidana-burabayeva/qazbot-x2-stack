# Адаптер движения X2: `/cmd_vel` в MC (Задачи C и E)

> Актуализация 2026-10-21: нижележащая таблица — исторический аудит.
> Текущий вход — /qazbot_d1_map/cmd_vel_authorized через goal_coordinator.
> Имя узла motion_adapter, запуск через ws/src/navigation/run_x2_driver.sh.
> Восемь повторов УДАЛЕНЫ. С 2026-11-06 (T5, решение оператора, вариант C) live:=true один раз за процесс
> автоматически, как только обнаружен сервис SDK, выполняет последовательность AgiBot-примера
> mc_locomotion_velocity.py: ADD; если код ADD != 0 — ровно один ENABLE («likely already registered»);
> ENABLE != 0 или исключение — registration=failed, издателя MC нет, больше вызовов нет. Никогда DELETE.
> Причина: после перезагрузки источники MC сбрасываются (AimDK 5.1.3), статический ENABLE падал с code=1.
> registration_action принимает только add_then_enable. ~/register оставлен для совместимости (отказ после запуска).
> Успех определяется response.header.code == 0, pending/ошибка ничего не включают.
> Неизвестный DDS-издатель запрещает движение сразу, исключения на 10/15 секунд удалены.
> После регистрации motion_armed=false: команды от прежней цели отбрасываются.
> Только ~/arm_motion для новой цели при текущих здоровых входах открывает допуск.
> stop/перехват закрывают его; resume не открывает допуск и не возобновляет цель.
> Старый grace относится только к начальному получению управления. После первого
> наблюдения своего источника переход к rc защёлкивается немедленно.
> В простое и при завершении из простоя команды MC не публикуются.
> Проверки: **43 unit** (37 + 6 `test_dry_run_shadow`); adapter_registration_fake_03 — 28; adapter_driver_gate_01 — 14;
> adapter_ros_explicit_01 — 7 dry ROS; реальная цепочка `nav_e2e_real_dryrun_08` — 160/160 (настоящий адаптер live=false). Это НЕ физическая SDK-приёмка.
> Реальная регистрация/скорости требуют отдельного согласования.
> Временные границы MC/state/trust остаются кандидатами до аппаратной квалификации.
>
> Актуализация 2026-10-21 (вечер), сверено с кодом:
> - **dry_run теперь «теневой» (shadow)**: те же состояния idle/active/latched, те же отказы (`localization_untrusted`,
>   `foreign_velocity_publisher`, `vendor_autonomy_active`, …), пачка нулей (зеркалируется в `~/dry_run_cmd`), защёлки, `motion_armed` обязателен.
>   В dry_run нет только: издателя MC, flock, клиента регистрации, `control_not_acquired` (незарегистрированный источник MC выбрать не может).
>   Принимается источник MC, наблюдавшийся при активации (или наше имя); любой другой источник при active даёт `operator_takeover`.
>   Из-за этого прежние тесты «dry_run не защёлкивается / не шлёт нули» заменены (5 штук, см. отчёт implA).
> - **Перехват PS5 в dry-run виден только если MC сообщит смену источника.** Источник простоя по умолчанию уже `rc`, поэтому касание пульта при `rc`
>   в dry-run невидимо. Полностью наблюдаем перехват только в live после регистрации.
> - Явный путь драйвера в dry_run: `~/arm_motion` успешен при `registration=='dry_run'`; координатор принимает такой драйвер только с `allow_dry_run_driver:=true`
>   (по умолчанию false) и только если адаптер сообщает `live=false`, `mode=dry_run`, `ready`. Это не даёт доступа к MC.
> - `sdk_qazbot_nav2` с приоритетом 30 — только параметр конфигурации, не разрешение на регистрацию источника.

## 3. Дизайн адаптера

Чистая логика отделена от ROS (`AdapterCore`) и тестируется без робота.

```
Nav2 controller --> velocity_smoother --> /qazbot_d1_map/cmd_vel --> goal_coordinator (шлюз) --> /qazbot_d1_map/cmd_vel_authorized
   --> x2_motion_adapter --> live: /aima/mc/locomotion/velocity ; dry_run: ~/dry_run_cmd
                               ^ /aima/mc/common/state (10 Гц: источник, поза, FSM, границы)
                               ^ /qazbot_d1_map/tf (свежесть map->odom)   ^ localization_trust/trusted   ^ опрос графа (издатели MC-топика)
```

Режимы:
- **`dry_run` (по умолчанию).** Издатель в MC **не создаётся**, источник не регистрируется, блокировка не берётся.
  Решения публикуются в `~/dry_run_cmd` (Twist) и `~/status` (JSON). Движение невозможно по построению. Внутри работает та же машина состояний
  idle/active/latched («shadow»): отказы, защёлки, пачка нулей и обнаружение смены источника ведут себя как в live (различия описаны в шапке).
- **`live:=true`.** Берёт эксклюзивную блокировку владельца и создаёт клиента регистрации. Источник регистрируется автоматически один раз
  при обнаружении сервиса SDK (ADD, при ошибке один ENABLE, без повторов); издатель MC создаётся только после ACK `header.code == 0`; публикует только пока
  есть свежая валидная ненулевая команда и `motion_armed`.

Состояния машины: `idle`, `active`, `latched`; режим (`status.mode`) `dry_run` или `live`.

Правила:
1. Конец цели (нулевая или устаревшая команда): 5 нулей, затем тишина, состояние `idle`. Это не авария.
2. **Защёлка** (`latched`, без движения до `~/resume`): перехват пультом или приоритетным источником
   (`operator_takeover`), управление не получено за 0,5 с (`control_not_acquired`), робот не стоит (`robot_not_standing`),
   FSM не `STABLE/MOVING` (`mc_fsm_not_stable`), состояние MC старше 0,5 с (`mc_state_stale`), потеря локализации
   (`localization_lost`, `map→odom` старше 1 с), чужой SDK-источник активен (`foreign_sdk_source_active`), боковая скорость
   (`lateral_not_allowed`), нечисловое значение (`non_finite_command`), `~/stop`.
3. После `~/resume` команды, отправленные до подтверждения, игнорируются: цель Nav2, продолжавшаяся во время защёлки,
   сама робота не запустит.
4. Значения не меняются. Выше границ MC срезаются до границы и считаются (`saturated`), малые не поднимаются.
   Дополнительные отказы, действующие в обоих режимах: `localization_untrusted` (вердикт trust отсутствует, старше 0,6 с или `false`),
   `foreign_velocity_publisher` (чужой издатель MC-топика по опросу графа, в том числе неизвестное имя, до первого опроса и при сбое опроса),
   `vendor_autonomy_active` (источник MC `pnc`).
5. Имя источника проверяется: префикс `sdk_`, встроенные (`linkswarm, rc, app_proxy, vr, interaction, pnc`) запрещены.
6. Один владелец: `flock` на `~/control_backend/run/x2_motion_owner.lock` (только live) и отказ, если в MC уже активен чужой
   SDK-источник. **Ограничение:** flock кооперативный: `ContinuousWalker` должен брать ту же блокировку, иначе защита от него только на уровне
   MC и опроса графа DDS (диагностика, не аппаратная гарантия; `GetCurrentInputSource` адаптером не используется). Подробно и с границами:
   `X2_LOCALIZATION_TRUST.md`, раздел «Единственный владелец автономного движения». Это пока не сделано (код ходока не здесь).
7. Конец цели после `~/stop`/`resume`: `resume` не открывает допуск и не возобновляет цель; новую цель открывает только `~/arm_motion`.

Параметры узла: `live` (false), `cmd_vel_topic`, `source_name`, `priority` (30), `controller_hz` (20, отсюда
`cmd_timeout = 3 / hz = 0,15 с`), `allow_lateral` (false), `require_localization` (true), `require_trust` (true), `tf_max_age_s` (1,0), `trust_topic`, `lock_path`,
`registration_action` (add_then_enable, единственное значение), `vendor_publishers` (список регулярных выражений). Кандидатные границы по времени в коде: состояние MC 0,5 с,
вердикт trust 0,6 с, `acquire_grace_s` 0,5 с (только live).

Не сделано намеренно: нет планирования, нет `SetMcAction`, нет отключения источника при выходе (источник остаётся
зарегистрированным и молчит), порог по ковариации AMCL не задан (нет обоснованного значения, нужен допуск из измерений).
