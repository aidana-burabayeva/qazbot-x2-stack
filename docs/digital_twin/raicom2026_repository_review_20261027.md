# raicom2026-agibot-X2: что полезно QazBot — 27.10.2026

Проверен `main` на commit **a97761820b398b6cab12b632ce9f313c394eeb7e** из [AgiBot-Community/raicom2026-agibot-X2](https://github.com/AgiBot-Community/raicom2026-agibot-X2/tree/a97761820b398b6cab12b632ce9f313c394eeb7e). Основной вывод: полезен как прикладной пример X2/AimDK и источник контрольных гипотез. Готового решения наших поворотов, выбега и точности 10 см / 0.1 рад здесь не подтверждено.

Подробно прочитаны навигаторы, командный мост, мосты TF/odom, активные конфиги и launch, пример штатной навигации и координатор. Остальные подсистемы оценены по структуре/документации, полноценный аудит ASR, зрения и захвата не выполнялся. Запусков внешних ROS-нод, bringup, регистрации источников MC и движения не было. Внешние README использовались как документация, не как инструкции к выполнению.

## 1. Как действительно устроена навигация

В рекомендуемом соревновательном запуске:

`штатная локализация App / TF map→base_link → tf_pose_bridge → task1_pose_nav или service_pose_nav → /cmd_vel → cmd_vel_bridge → установленный MC`.

[Launch](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/launch/task1_app_ready.launch.py) запускает три собственные ноды. Навигатор — конечный автомат WAIT_POSE / WAIT_GOAL / ALIGN_TO_GOAL / DRIVE_TO_GOAL / FINAL_ALIGN. Скорость пропорциональна расстоянию/угловой ошибке с ограничениями и нижним ненулевым порогом. В этой цепочке нет Nav2 controller_server, costmap-проверки препятствий, progress checker, модели выбега или обратной связи по измеренной скорости. Поиск max_accel/decel/ruckig в проверенном race_task не выявил соответствующей логики.

Отдельный [Nav2 test launch](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/launch/task1_nav2_test.launch.py#L58) включает внешнее `lidar_localization_ros2` и demo-одометрию, интегрирующую cmd_vel. Этот пакет не представлен в дереве src данного репозитория. Такая demo-одометрия не измеряет исполнение MC. Сам launch одновременно содержит мост к SDK; его нельзя считать готовым изолированным физическим twin.

`my_perfect_nav2_versions.txt` — перечень установленных ARM64 пакетов Nav2 1.1.18. Это не набор проверенных параметров и не основание заменять наш Nav2/Smac overlay. MC через SDK используется как готовый нижний уровень; исходников исправления его походки в проверенных модулях нет.

## 2. Что имеет смысл использовать

| Что | Польза | Как адаптировать к нашим требованиям |
|---|---|---|
| Нижний ненулевой ввод MC | В bridge явно учтён deadband: малая команда поднимается до min_forward/min_angular | Калибровать реальные пороги .66 отдельно по направлениям. Контроллер должен знать преобразование; скрыто повышать команду после Nav2 нельзя |
| Отдельные фазы наведения, ходьбы и финального угла | Хороший промежуточный эталон между прямой SDK-пробой и полной Nav2-цепочкой | Собственная SIM-реализация через наш адаптер, с остановкой по измеренной скорости, одновременной проверкой XY/yaw, ограничением попыток и проверками препятствий |
| Фиксация направления финального поворота | В task1 добавлен принудительный left/right; это явная работа с выбором направления | Фиксировать выбранный знак на один манёвр, особенно около ±π; выбирать по измерениям, а не всегда идти влево |
| Раннее обнуление на подходе | При distance≤0.25 навигатор уже прекращает ходьбу, что может частично компенсировать физический выбег | Проверять 0.25 м как гипотезу зоны начала торможения, сохраняя отдельный конечный допуск 0.10 м. В коде репозитория эти два понятия не разделены |
| Родная leg_odometry | Есть явный потребитель /aima/mc/leg_odometry с chest-IMU фреймом | Сохранять source timestamp и делать настоящее преобразование точки груди в нужный body frame; сравнивать с LIO, не переименовывать фреймы |
| Штатный PNC | Пример PncTaskRequest для start/pause/resume/stop по /aima/te/pnc_task_request | Возможный отдельный контроль против нашей Nav2 при доступной штатной карте/локализации, с task_id, обратной связью и подтверждённой отменой |

Минимумы 0.2 м/с и 0.1 рад/с в [SDK-примере](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/py_examples/py_examples/mc_locomotion_velocity.py) — ограничение ввода примера, не измеренная характеристика нашего MC. На .66 и в нашем MC-стенде уже обнаружены другие эффективные пороги/скорости. Не следует автоматически считать angular=0.1 устойчивым вращением ног.

Интерфейс PncTaskRequest уже есть и в нашем установленном AimDK (`runtime_x86/run/aimdk/install/py_examples/.../navigation.py`). Это не новая возможность, которую нужно обязательно копировать из этого проекта. Внешний вариант добавляет непрерывную отправку задания; готового контроля результата/обязательного stop при выходе из меню там нет.

## 3. Почему не подходит замена целиком

### Более мягкий контракт точности

В [рекомендованном YAML](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/config/competition_official_voice_nav.yaml#L42):

- goal_xy_tolerance=0.25 м;
- goal_yaw_tolerance=0.35 рад, около 20°;
- forward=0.20…0.30;
- angular=0.10…0.35.

Это существенно отличается от наших 0.10 м / 0.10 рад. Максимальная angular=0.35 также не является доказанным решением ситуации, где наш MC прекращал вращение уже при 0.5. Нужна версия MC и сопоставимые физические измерения; в race_task/test лежат lint/copyright/PEP-проверки, не измерения исполнения движения.

### Повторная публикация старого измерения как свежего

[tf_pose_bridge](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/race_task/tf_pose_bridge.py#L38) запрашивает latest TF и ставит в PoseStamped текущее время. [robot_odom_bridge](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/race_task/robot_odom_bridge.py#L109) переиздаёт последний odom с новым временем без возрастного предела. Навигаторы проверяют время приёма PoseStamped, игнорируя header.stamp. При сохранённом старом TF/odom отсутствие новой локализации может скрываться.

В этом же репозитории есть более корректный [LocalizationTfNode](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/map_tf_distribution/map_tf_distribution/localization_tf_node.py): он сохраняет tf.header.stamp. Но для безопасного заимствования нужна и проверка source age в потребителе. Рекомендуемый task1 launch использует другой, переотмечающий время tf_pose_bridge.

### Финальный угол может дать ложное достижение цели

В [FINAL_ALIGN](https://github.com/AgiBot-Community/raicom2026-agibot-X2/blob/a97761820b398b6cab12b632ce9f313c394eeb7e/src/race_task/race_task/task1_pose_nav.py#L358) условие reached проверяет только yaw. XY не проверяется повторно после перехода к финалу, измеренная остановка/выдержка не требуются. Это повторяет класс проблемы, который мы уже исследовали со stateful XY-latch. Аналогичное условие есть в service_pose_nav.

### Прочие ограничения

- Принудительный левый поворот при ошибке -0.4 рад даёт управляющую ошибку +5.883 рад: это может означать почти полный круг. Само наличие такой функции не доказывает, что асимметрия скорости исправлена.
- Цель в чужом frame только вызывает warning; координаты всё равно используются как map. Преобразования или отказа нет.
- robot_odom_bridge меняет frame_id/child_frame_id без преобразования pose/twist. При совпадении исходных фреймов это не проблема; при смене chest на pelvis/base_footprint это создаст ошибку.
- Четыре одновременные QoS-подписки на один odom — средство разведки интерфейса, а не подходящий штатный приёмник: совместимые читатели могут дублировать данные.
- В cmd_vel_bridge нет эквивалента нашего контроля свежего состояния MC, владельца источника, dry-run и допуска. Результат register_input_source не используется конструктором как условие разрешения публикации; код ответа сервиса не подтверждается как успешный.
- Обработка min/max сначала ограничивает максимум, затем поднимает до минимума. При ошибочной конфигурации min>max выход превысит max. В проверенном штатном YAML эти параметры согласованы; это дефект проверки параметров, а не зафиксированное превышение в данном YAML.
- Два навигатора используют общий /cmd_vel без жёсткого арбитра. Нормальный WAIT_GOAL молчит, но ветки отсутствия/устаревания позы публикуют ноль до проверки активности цели. Поэтому молчание неактивного источника обеспечено не во всех ветках.
- Потеря свежести позы временно обнуляет выход, затем старая цель может продолжиться после возврата позы; отдельного latched reset/new-goal контракта здесь нет.

## 5. Что ещё может пригодиться

- x2_ik_sdk: позиционная IK двух рук, FK, порядок arm_pos[14], ограничения суставов и чисто кинематическая URDF omnipicker. README прямо отмечает, что IK с одновременным ограничением ориентации ещё не реализована. Это потенциально полезно для манипуляции, но не готовая инерциальная модель нашего двойника; вариант робота/рук должен совпадать.
- ASR/VAD, выключение микрофона во время TTS и движения, локальные whitelisted intents — полезные архитектурные примеры для диалога. Зависимости/модели нельзя устанавливать поверх рабочего ROS-окружения вслепую.
- Ruckig — отдельная библиотека; в проверенной цепочке race_task она не задаёт рампы ходьбы. Её наличие не является готовой компенсацией выбега MC.

## 6. Приоритет для QazBot

Первым экспериментом полезен минимальный позиционный контроллер как промежуточная диагностика: та же фактическая поза, наш адаптер, проверка source freshness, раннее торможение, одновременные XY/yaw/stop и ограниченные коррекции. Сравнить его с прямым SDK и полной Nav2 на одинаковом стенде. Начало торможения и конечный допуск задавать отдельно; 0.25 м из проекта — гипотеза для торможения, а не новый критерий успеха.

Второе направление — независимое сравнение нативной odometry/штатного PNC с нашей цепочкой при доступном роботе, корректной штатной карте и согласовании фреймов. Оно может отделить свойства MC от верхней навигации, но не заменяется интегрированием cmd_vel.

Наши adapter/watchdog/source checks, временные метки и одновременная проверка XY/yaw остаются. Авторскую реализацию/числа можно использовать как справочник; интеграцию следует писать под наш контракт, без переноса этих дефектов.
