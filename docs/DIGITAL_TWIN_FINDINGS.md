# QazBot X2: требования к цифровому двойнику по данным реального робота (по 2026-10-29)

Назначение: перечислить, что симуляция (Virtual MC / официальный MC + MuJoCo, см. [digital_twin/README.md](digital_twin/README.md)) должна воспроизводить, чтобы в ней проявлялись те же отказы, что на реальном X2 (agi@192.168.1.72). Все числа взяты из записей реального робота. Сначала откалибровать модель под этот документ, потом прогонять регрессию стека Nav2.

Метки достоверности:
- **[M]** измерено на роботе (файл указан);
- **[D]** выведено из измерений (расчёт или сравнение);
- **[E]** оценка или допущение (не измерено, уточнить).

Сокращения путей:
- `EV29` = [evidence/nav_session_20261029](evidence/nav_session_20261029/);
- `EV28` = [evidence/nav_session_20261028](evidence/nav_session_20261028/);
- `P19` = `EV29/reports/20261029-p19-rotation.md`;
- `P20` = `EV29/reports/20261029-p20-yawloop.md`;
- `P20live` = `EV29/calib/p20_yaw_test_20261029_215906_summary.json` (+ `_215646_` для теста 1).

Командный путь на роботе: RPP -> velocity_smoother -> Goal Coordinator -> `cmd_vel_authorized` -> x2_motion_adapter -> MC `/aima/mc/locomotion/velocity` (50 Гц, source prio 30; RC prio 80). Модель MC должна принимать именно `McLocomotionVelocity` с этим арбитражем источников, а не идеальный `cmd_vel`.

## (a) Модель отклика MC по yaw-rate (главный источник отказов)

### a1. Статическая характеристика команда -> устойчивая скорость, из STAND_DEFAULT

Скорость берётся по native odom (поза груди `lidar_imu_chest_front`), окно 1.5-6 с, путь через adapter без yaw-loop.

| w_cmd, рад/с | CW (факт) | CCW (факт) | Доля stall (CW / CCW) | Источник |
| --- | --- | --- | --- | --- |
| 0.2 | -0.20 первые 1.5 с, затем **0.00** | +0.22, затем **0.00** | 0.94 / 1.00 | [M] P19 часть 1, `EV29/calib/p19_turn_calib_20261029_184054_summary.json` |
| 0.4 | **-0.27** | **+0.10** | 0.06 / 0.39 | [M] то же |
| 0.6 | **-0.54** (первые 1.5 с -0.72) | **+0.53** (только 1.5-3.5 с, abort по дрейфу) | 0.00 / 0.12 | [M] то же |
| 0.8 | не измерено | **1.25** (переход STAND->LOCOMOTION через +0.3 с) | — / 0 | [M] P19 часть 2, `EV29/calib/p19_turn_calib2_20261029_185054_summary.json` |
| 1.0 | не измерено | **1.87** | — / 0 | [M] то же |

Требования к модели:
- **Мёртвая зона зависит от направления.** Чтобы поворот держался: CW примерно от 0.4 [M], CCW от 0.6 [M]. CCW 0.4 слабый, 39 % stall [M]. При 0.2 оба направления поворачивают на 0.2-0.3 рад и встают [M].
- **Перерегулирование выше порога:** 0.8 -> 1.25 рад/с (1.56x), 1.0 -> 1.87 рад/с (1.87x) [M]. Характеристика нелинейная и неоднозначная: малая команда даёт 0, большая даёт 1.6-1.9x.
- Для CW 0.8/1.0 данных нет. В P20 их экстраполировали (CW 0.8 -> 1.2, 1.0 -> 1.8) [E].
- **Прямой MC совпадает** (adapter не участвует, источник `sdk_qazbot_calib_direct`, 10 с на шаг): CCW 0.2 -> 0.00 (сначала -15 град «не в ту сторону», потом возврат 13-16 град); 0.3 -> 0; 0.4 -> 0.05; 0.5 -> 0.01; 0.6 -> 0.35 [M] (`EV29/calib/p19_mc_direct_20261029_185327_summary.json`). Модель должна давать эти числа без adapter.
- Расхождение с 2026-10-22 (S3b): CCW 0.6 -> 0.29 рад/с, CW 0.6 -> **-0.92** рад/с, CW 0.5 не поворачивал (8 град за 13 с) [M] (`EV28/orchestrator/DECISIONS.md` 19:5x). Значит, разброс между сессиями и днями заметный. Модели нужен параметр «сессия» или шум усиления ±40 % [D].

### a2. Зависимость от состояния походки (STAND_DEFAULT против LOCOMOTION_DEFAULT)

| --- | --- | --- | --- | --- |
| CCW 0.6 после ходьбы 0.3 м/с 1 с | 0.65 | **0.37** | 0.27 | [M] P19 calib2 |
| CCW 0.6 после ходьбы, затем пауза 0 0.8 с («kick») | 0.34 | **0.34** | 0.38 | [M] P19 calib2. STAND за 0.8 с не наступил |

| CCW 0.6 в реальных goals (RPP rotate-to-heading после ходьбы) | ~0.28 первые <1.5 с | **0.00, 96 % stall** (n=1499, ~75 с) | 0.96 | [M] P19 (A), bag `goal_bag_mcap_143120` |
| CW 0.6 в goals | -0.61 | -0.55 | 0.12 | [M] то же |
| CCW 0.5 в goals | — | 0.01 | 0.70 | [M] то же |

Требования к модели:
- Ввести состояние MC ∈ {PASSIVE, DAMPING, STAND_DEFAULT, LOCOMOTION_DEFAULT}.
- После ходьбы (LOCOMOTION) снижать усиление поворота до 0.3-0.6 от значения из STAND [D].
- Для **CCW держать stall**: примерно через 1.5 с непрерывной команды +0.6 скорость падает до 0 и не восстанавливается, пока команда не меняется (в goals держалось 30 с) [M].
- Старт из покоя после паузы ≥2.4 с поворачивал: +0.6 рад/с, 1.3 рад за 2.4 с [M] (P19 (A), goal 1793268764.6).
- Переход STAND->LOCOMOTION начинается примерно через 0.3 с после ненулевой команды [M] (P19 calib2).
- Пауза 0.8 с не возвращает робота в STAND [M].
- Чистое время запаздывания MC ~0.5 с [M/E] (P20, «measured MC dead time ~0.5 s»). В офлайн-модели P20 использовали 0.4 с + лаг первого порядка 0.2 с [E].
- Рябь походки: после LPF 0.25 с ±0.2 рад/с [M]. В модели P20 ±0.35 рад/с с частотой 1.1 Гц [E].

### a5. Арбитраж источников MC (для сценариев отказа)

- После перезагрузки MC в PASSIVE_DEFAULT. ADD SDK-источника работает только после ручного stand оператором с RC [M] (HANDOFF 10-29, P15).
- После DELETE (code 0) MC может «залипнуть» на старом источнике (`sdk_qazbot_calib_direct`) до касания RC. Тогда adapter показывает `foreign_sdk_source_active`, ready=false [M] (P19, «State after the tests»).
- Adapter при выходе не делает DELETE: перезапуск требует ручного DELETE + ADD [M] (`EV29/logs/p20_restart_run.txt`).
- RC prio 80 > SDK 30. Перехват по RC (takeover latch) на железе не доказан [M/E].

Сначала каждый сценарий должен **падать** на модели без поправок (с прежним круглым footprint, adapter без yaw-loop и т. д.) так же, как падал на роботе. Это проверка достоверности модели. Только затем он должен проходить с текущим конфигом.
