## 2026-10-22: READY / MOTION_OK (решение пользователя «Simplify Localization Trust») — действующая модель
Этот раздел имеет приоритет над таблицей ниже там, где они расходятся (таблица описывает сами проверки и пороги, они не менялись).
- **READY** (защёлка). Ставится на первой оценке после `~/confirm_anchor`, где чисты проверки ворот: T0/T1 (свежесть),
  T2 (ковариация), T3 (частицы), T4 (оценка скана/падение; `baseline` НЕОБЯЗАТЕЛЕН — без него порог `hit_min_abs` = 0,35),
  T5 (нет скачка), T6 (поза всё ещё у подтверждённого якоря), T8 (карта совпадает). Пока ворота не чисты — READY=false,
  причины видны в `status.reasons` (без таймаута; оператор может повторить подтверждение).
- **READY снимается только**: подтверждённым скачком T5 (`T5_map_odom_jump` при свежем `map→odom`, прежние пороги
  0,10 м / 0,10 рад за 1 с), T8 (карта не совпадает / не получена), новым `initialpose` (подписка `<ns>/initialpose`),
  новым `confirm_anchor` (повторные ворота), потерей входов T0/T1, которая **ещё есть в момент запроса новой цели**
  (координатор вызывает `~/arm_check` и при отказе по свежести; транзиентная потеря сама READY не снимает).
  Восстановление READY — только оператор: `confirm_anchor` (после `initialpose`, если нужно).
- **MOTION_OK** = READY и нет причин T0/T1 (odom TF и сообщение, скан, `map→odom`, замороженный TF; свежесть AMCL —
  только по правилу «AMCL due»). Публикуется как `~/trusted` (контракт топика прежний). Стоящий робот без новых
  `amcl_pose` READY/MOTION_OK не теряет.
- **Диагностика** после READY: T2, T3, T4, T6, T7 → `status.diagnostics`; движение не останавливают. `arm_check`:
  неоднозначность (T7) больше не отклоняет цель, только запускает диагностику бюджета.
- Гистерезис `settling` (`stable_s` = 5 с) удалён (параметр оставлен для совместимости, не используется): после потери
  MOTION_OK цель прервана, координатор/адаптер в защёлке, старая цель не возобновляется; движение снова — только
  `resume` + НОВАЯ цель с проверкой на текущих данных. Дребезг входов даёт новую остановку, а не движение.
- `status` (JSON): `trusted`, `ready`, `motion_ok`, `ready_cause`, `reasons` (блокирующие + `not_ready:<причина>`),
  `diagnostics`, `metrics`.
- Тесты: `tests/loc_trust/test_ready_motion.py` (9) + прежние 56 (переписаны ожидания: T2/T3/T4/T6/T7 → `diagnostics`,
  settling → немедленное восстановление MOTION_OK, ворота READY). Адаптер не менялся.

## 2026-10-22: сохранение подтверждённой позы между перезапусками (Step B, report locpersist §5/§8)
Цель: после перезапуска локализации оператору не нужно заново ставить позу в RViz. READY по-прежнему выдаёт только
оператор (`confirm_anchor`) + чистые ворота; критерии READY не менялись.
- **Запись** (`localization_trust_node.py`, параметр `pose_store`; по умолчанию `''` = выкл., `run_trust.sh` задаёт
  `~/.ros/qazbot_x2_last_confirmed_pose.json` = `pose_store.DEFAULT_PATH`, с учётом `ROS_HOME`). Пишется атомарно
  (`.tmp` + fsync + `os.replace`) только: (1) на фронте READY (после `confirm_anchor` и чистых ворот); (2) при штатной
  остановке узла (SIGINT), если последняя оценка READY и MOTION_OK и в `diagnostics` нет ничего, кроме `T4_no_baseline`.
  Каждый `amcl_pose` НЕ пишется. Содержимое: поза в `map` (= map→odom ⊕ odom→base_footprint), ковариация AMCL (6×6),
  sha256 изображения карты, `source` (`ready`/`shutdown`), время. Карта не совпадает (T8) — не пишется.
  ID запуска FAST-LIO недоступен, поэтому ветка «тот же запуск LIO: map→odom ещё верен» не реализована: всегда сеем позу в map.
- **Подстановка** (`localization.launch.py`, аргумент `seed_pose_file`, по умолчанию тот же путь; `seed_pose_file:=''`
  выключает): одноразовый `seed_pose.py --from-file <файл> --map-yaml <map_yaml>`. Если файл есть, читается, его
  `map_sha256` совпадает с картой `map_yaml` и поза/ковариация корректны — ОДИН `initialpose` с сохранённой ковариацией.
  Ждёт по графу (без таймаута), пока в графе есть подписчик `amcl` (`/qazbot_d1_map`) и все подписчики сопоставлены;
  AMCL, получивший позу до активации, применяет её при активации. Нет файла / битый / другая карта — ничего не публикуется,
  код выхода 0, в логе причина (`no_file`, `unreadable`, `map_sha256_mismatch`, `format`, `covariance`). Выход процесса
  не останавливает launch. `set_initial_pose` AMCL не используется (в humble ковариация нулевая).
- **Не даёт READY**: trust-узел обрабатывает сеянную позу как любой `initialpose` (`relocalize()`: якорь сброшен,
  `ready_cause=initialpose`). READY только после `confirm_anchor` и чистых ворот T2/T3/T4/T5/T8 на этой позе.
- **Процедура оператора после перезапуска локализации** (робот стоит):
  1. Запустить `run_localization.sh` как обычно. В выводе `seed_pose.py`: `"one hypothesis published"` (поза подставлена)
     или `"nothing seeded ... reason"` (поставить позу вручную, как раньше: RViz «2D Pose Estimate» / `seed_pose.py --x ...`).
  2. Если trust-узел не перезапускался — он сам увидит `initialpose` и снимет READY; если перезапускался — `run_trust.sh`.
  3. Не отправлять `initialpose` повторно. Стоящий AMCL сам не обновляется: вызывать
     `/qazbot_d1_map/request_nomotion_update` (std_srvs/Empty), пока в `status` не уйдут `T2_covariance`/`T3_particles`
     (20:06-20:08 понадобилось ~30 обновлений) и `T4_scan_score` (скан ложится на карту, см. RViz).
  4. Проверить совпадение скана с картой (метка на полу / RViz) и вызвать `confirm_anchor`. READY придёт на ближайшей
     чистой оценке; при этом подтверждённая поза запишется заново.
  5. Если `T4_scan_score` не уходит или скан явно смещён — робот двигали, пока стек был выключен: поставить позу вручную
     (шаг 1, ручная ветка) и снова `confirm_anchor`. Сеянная поза никогда сама не становится якорем.
- Тесты: `tests/loc_trust/test_pose_persist.py` (14: атомарная запись, только на фронте READY, несовпадение sha карты,
  битый/отсутствующий файл, сохранение при остановке, сеянная поза без READY, отказы `seed_pose.py`, аргумент и
  защита launch) и `test_seed_ros.py` (1, только на изолированном графе `ROS_DOMAIN_ID=89 ROS_LOCALHOST_ONLY=1`: одна
  публикация с сохранённой ковариацией и только после появления `amcl`). На роботе не проверялось.

## Проблема
Свежий `map→odom` значит лишь, что AMCL ещё публикует. После ложной привязки (симметрия, одна стена в секторе лидара ±52°,
неверная начальная поза) AMCL продолжает публиковать преобразование. Движение возобновилось бы на неверной позе.

## Критерий: движение разрешено, только пока выполнены все условия
Значения по умолчанию из `TrustConfig` (`loc_trust.py`). Причина отказа — строка в `status.reasons`.

|---|---|---|---|

| T1 | `T1_odom_stale`, `T1_odom_message_stale`, `T1_tf_stale`, `T1_scan_stale` | возраст `odom→base_footprint` (TF) и сообщения `odom_level` ≤ 0,5 с; `map→odom` ≤ 1,0 с; скан ≤ 0,5 с | 0,5 / 0,5 / 1,0 / 0,5 с |
| T1 | `T1_amcl_pose_stale`, `T1_particle_cloud_stale` | `amcl_pose` и `particle_cloud` ≤ 3 с **только при движении** (AMCL публикует их лишь при обновлении фильтра, то есть после движения); `amcl_pose` ни разу не получен — отказ всегда | 3 с |

| T5 | `T5_map_odom_jump` | скачок `map→odom` за 1 с | ≤ 0,10 м и ≤ 0,10 рад |
| T6 | `T6_no_anchor`, `T6_anchor_disagreement` | якорь: поза подтверждена оператором (`confirm_anchor`); затем ‖поза − (якорь ⊕ смещение LIO)‖ | xy ≤ 0,15 м, yaw ≤ 0,10 рад; **рост допуска с путём в коде равен 0** (`anchor_xy_per_m = 0`, `anchor_yaw_per_rad = 0`), тест `test_no_unmeasured_tolerance_growth` это закрепляет |

| — | `settling` | доверие возвращается только после 5 с непрерывно чистой оценки (`stable_s`) | 5 с |

Прежняя версия документа указывала для T6 «+0,03 м на метр» и для T7 «≤ 2 м» как действующие. В коде этого нет: допуск якоря
не растёт с путём, а 2 м не включены по умолчанию.

Вердикт (`~/trusted`, 5 Гц) потребляют адаптер и координатор; возраст вердикта > 0,6 с (`trust_max_age_s`) считается как «не доверяем».
После отказа адаптер, сверх 5 с стабильности, остаётся в защёлке до явного `~/resume`, а координатор принимает только НОВУЮ цель
(см. «Защёлка и возобновление»).

Почему именно якорь: LIO не использует карту. Скольжение вдоль одной стены даёт идеальную оценку скана (тест: >0,9 на всём
пути), ковариация и скачки тоже в норме. Только расхождение с якорем плюс одометрией это показывает (тест: срабатывает
при дрейфе < 0,25 м). Ложный скачок на 1 м: T5 срабатывает сразу, после окончания окна T6 продолжает блокировать
(тест `test_false_global_lock_jump_never_regains_trust`). Ослабление допуска якоря ломает эти два теста (проверено мутацией).

## Статус параметров: что подтверждено, что EXPERIMENTAL
Ничто в таблице выше не откалибровано на X2. Явно помечены в коде и в `status.experimental`:
- `degenerate_budget_m` (по умолчанию 0,0). `EXPERIMENTAL_DEGENERATE_BUDGET_M = 2.0` в `loc_trust.py` — кандидат на опцию
  «2 м пути по одометрии LIO после неоднозначной arm-проверки»; включается только параметром узла и пишет предупреждение в журнал.
  Основание не включать по умолчанию: старт фикстуры на карте D1 не неоднозначен (конкурент 0,34 против 1,0 у номинала, офлайн).
- `frozen_window_s`, `frozen_motion_min_m`, `frozen_motion_min_rad` (T1_tf_frozen).
- Пороги T2–T5 и абсолютный пол 0,35: кандидаты до записи неподвижного робота (F0, `X2_FIRST_PHYSICAL_TEST_PLAN.md`).
- Допуск якоря xy 0,15 м / yaw 0,10 рад: кандидат; дрейф LIO в абсолютных метрах не измерен (по twist ~0,5 %).

- В живом стеке (domain 0) trust-узел запущен (PID 388248, `run_trust.sh`), но доверие там `false`: нет начальной позы AMCL и

- Из-за `T4_no_baseline` доверие невозможно, пока не выполнена калибровка (`~/baseline_start` → `~/baseline_finish`, ≥ 20 отсчётов).

## Операторские сервисы trust-узла (`/qazbot_d1_map/localization_trust/…`)
`baseline_start`, `baseline_finish` (медиана оценки скана в подтверждённой позе, робот стоит), `confirm_anchor`, `arm_check`
(~0,9 с на Jetson, поэтому сервисы работают в отдельной группе на втором потоке и не задерживают вердикт 5 Гц).

## Защёлка и возобновление
- Любой отказ trust при активной цели: координатор закрывает шлюз команд (`gate=false`), публикует нулевой Twist, запрашивает
  отмену внутренней цели, ставит `latched`. Адаптер при том же отказе защёлкивается сам (`localization_untrusted` или
  `localization_lost`) и выдаёт пачку из 5 нулей.
- `goal_coordinator/resume` (и `motion_adapter/resume`) снимают защёлку, но **не возобновляют старую цель**: координатор не хранит
  цель и не воспроизводит команду, адаптер игнорирует команды со штампом до `resume`, а допуск `motion_armed` после `resume`
  равен false. Движение возможно только после НОВОЙ принятой цели (её приём вызывает `arm_check` trust, `arm_motion` адаптера и
  ожидание нового вердикта trust).
- Условие `coordinator/resume`: защёлка есть, цели нет, последняя команда источника была нулём, доверие текущее. Иначе отказ.

## Единственный владелец автономного движения: что есть и чего нет
Что реально существует в коде (проверено по `x2_motion_adapter.py`, `goal_coordinator.py`):
1. **flock** `run/x2_motion_owner.lock` (`OwnerLock`): берётся адаптером **только в режиме `live:=true`**. Кооперативен: защищает только
   тех, кто сам его берёт. `ContinuousWalker` (код на .89, на .66 его нет) его может не брать. Не берётся в `dry_run`.
2. **Опрос графа DDS** раз в 1 с (`get_publishers_info_by_topic('/aima/mc/locomotion/velocity')`): любой издатель вне списка вендорских
   (`aimrt_planning_planning_node\d*`, `soc\d_rc\d*`, `app_proxy`, `soc\d_interaction_slave\d*`) даёт `foreign_velocity_publisher`.
   Издатель с неизвестным именем (`_NODE_NAME_UNKNOWN_`), до первого опроса (`graph_unobserved`) и сбой запроса (`graph_query_unavailable`)
   тоже запрещают движение. **Таймерных исключений нет** (старые 10 с и 15 с `discovery_pending` удалены из кода; прежняя версия этого документа
   их ещё описывала). Это **диагностика и отказ при обнаружении, а не аппаратная гарантия**: задержка обнаружения до ~1 с, издатель без
   узла в графе невидим, процесс, опубликовавший между опросами, не виден.
3. **Арбитраж источников в MC**: приоритет `rc` 80 перебивает SDK-источник (наш 30). Адаптер читает `McCommonState.input_source` (10 Гц);
   `pnc` даёт `vendor_autonomy_active`, чужой SDK-источник даёт `foreign_sdk_source_active`, смена источника с нашего на другой при движении даёт
   защёлку `operator_takeover`. Именно MC, а не наш код, решает, чьи команды исполняются.
4. **`GetCurrentInputSource`** используется только диагностическим `read_motion_state.py`; адаптер его не вызывает. Это диагностика.
5. **Координатор**: на `<ns>/cmd_vel` должен быть ровно один издатель, и его GID не должен меняться (`command_publisher_count`,
   `command_publisher_changed`). Это тоже опрос графа (в Humble rclpy не передаёт `MessageInfo`) и тоже не атомарно.
6. **Машина состояний** адаптера (idle / active / latched) и явные `stop`, `resume`, `arm_motion`.

Чего нет и что нельзя заявлять: атомарного владения аппаратным каналом; защиты от процесса, не знающего о flock и не издающего в видимый граф;
**наблюдаемости перехвата пультом в dry-run, если MC уже держит `rc`**: источник простоя по умолчанию `rc` (`CURRENT_CONSTRAINTS.md`),
поэтому касание PS5 при `rc` не меняет `input_source` и в dry-run невидимо; оно заметно, только если MC сообщит смену источника. Полностью
наблюдаем перехват лишь в live после регистрации (S4 плана). `sdk_qazbot_nav2` с приоритетом 30 — **только параметр конфигурации**,
не разрешение регистрировать источник в MC.

Дополнительно стоит добавить flock в `ContinuousWalker` на .89 (нужен доступ).

## Заметка: 3D NDT как возможный второй слой (только дизайн, не реализовано)
Текущая локализация: FAST-LIO → `level_bridge` (срез облака, выровненный по гравитации) → виртуальный `LaserScan` → AMCL на 2D-карте D1.
Если F0 покажет, что AMCL недостаточен (устойчивая неоднозначность, дрейф, ошибка > допуска в целевых местах), возможен 3D NDT:
- **D1 не может построить 3D-карту** (2D лидар/SLAM-карта). 3D-карту должен построить сам X2 (FAST-LIO накопленное облако), с последующей
  регистрацией в систему координат `map` карты D1 (по ≥ 3 опорным точкам с измеренной позой, затем проверка невязки на независимых точках).
- Получится два слоя представления: 2D occupancy (D1, общая для обоих роботов, источник планирования и T4/T8) и 3D NDT-карта X2 (только
  локализация). Их согласованность — отдельный риск (ошибка регистрации входит в ошибку позы), поэтому trust (T4, T6, T8) должен сравнивать
  оба результата, а не заменять один другим.
- Начинать только по результату F0: без измерения нельзя сказать, что AMCL недостаточен. Сейчас никакой код NDT не добавлен.
