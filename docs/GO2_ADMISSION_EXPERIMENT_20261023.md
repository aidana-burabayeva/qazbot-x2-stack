# Проверка допуска локализации по принципу Go2

> Обновление 26.10.2026: Go2 admission и автоматический stationary AMCL refresh теперь значения по умолчанию; отдельный профиль больше не нужен. Описание прежнего opt-in ниже оставлено как история эксперимента.

Пользователь запросил эксперимент, потому что текущий localization trust мешает проверке навигации. Реализация написана самостоятельно по принципу просмотренных localise action / action guard референса. Код и конфиги скоростей Go2 не копируются.

## Поведение профиля

`admission_policy=strict` остаётся значением по умолчанию. В эксперименте `go2`:

- После запуска требуется новое `initialpose` в текущем процессе. Уже доступный TF или кэшированный AMCL не дают начальный допуск.
- Валидная поза AMCL с source timestamp не раньше initialpose отмечает инициализацию. Следующие AMCL-сообщения продолжают обрабатываться. Отдельный `confirm_anchor` не нужен.
- Covariance, частицы, scan-score, коррекции map→odom, якорь и неоднозначность T2–T7 становятся диагностикой. Вычисление ambiguity в arm_check отключено для этого профиля.
- Custom AMCL-due/particle-due и frozen-TF проверки становятся диагностикой. Свежесть map→odom TF, odom/odom-message и scan остаётся обязательной с прежними порогами. Некорректные входы T0 и идентичность карты T8 блокируют.
- Новая initialpose сбрасывает предыдущую инициализацию. Потеря/несоответствие карты требует новой инициализации. Краткая потеря критических данных снимает MOTION_OK, восстановление данных возвращает его, но не возобновляет старую цель: существующие защёлки coordinator/adapter не менялись.
- В просмотренном Go2 localise action заканчивается после публикации initialpose/clear costmaps без нашего ожидания AMCL. Ожидание ответа AMCL и retained freshness/map checks — явно сохранённые адаптации X2; профиль не называется точной копией всего поведения Go2.
- Не меняются AMCL, RPP, smoother, скоростные пределы, footprint и управление MC. Профиль не очищает costmap автоматически: это могло бы скрыть реальные препятствия и не требуется для сравнения trust.

## Как воспроизвести

Из `~/control_backend`, после остановки предыдущего dry-run стека:

```bash
QAZBOT_TRUST_POLICY=go2 bash tools/stack/stack_up.sh go2_policy23
```

Скрипт всегда поднимает адаптер `live=false`; MC не регистрируется. Требуется задать действительную текущую позу через RViz `2D Pose Estimate`, затем проверить `/qazbot_d1_map/localization_trust/status`: `admission_policy=go2`, `initialized=true`, `ready=true`, `motion_ok=true` при свежих данных. Начальный допуск больше не требует схождения sigma или отдельного confirm_anchor. Произвольную позу ради READY задавать нельзя: проверка соответствия реальному месту остаётся за оператором.

Для параллельного наблюдения рядом со строгим режимом:

```bash
bash ws/src/navigation/run_trust_go2_shadow.sh ws/src/maps/first_map_nav2_v3/map.yaml
```

Его выходы имеют private namespace `/qazbot_d1_map/localization_trust_go2_shadow/...`; coordinator и adapter их не потребляют. Shadow должен стартовать до нового initialpose, поскольку не принимает старое сообщение за текущую инициализацию.

## Проверки и откат

46 адресных тестов проходят локально и на .66: сравнение допуска при covariance RViz, отсутствие частиц/якоря, сохранённые отказы по данным/карте, повторная инициализация, старый AMCL, нечисловые/нулевые quaternion, приём последующих AMCL и регрессия strict. Runtime-проверка и физический результат фиксируются отдельно; прохождение тестов не доказывает точность локализации.

Для возврата к strict: остановить эксперимент командой `bash tools/stack/stack_down.sh go2_policy23`, затем обычный `bash tools/stack/stack_up.sh НОВЫЙ_TAG` без переменной профиля. Исходники до установки сохранены на роботе в `~/control_backend/candidates/go2_admission_20261023/before.tar.gz`. Не распаковывать backup поверх чужих последующих изменений без сравнения.
