В исходном MPPI YAML отдельные ax/ay/az accel limits не заданы; из этого нельзя делать вывод о defaults неизвестной установленной версии MPPI.

`launch/nav2/navigation_launch.py` исходного проекта действительно связывает controller `cmd_vel_nav` → velocity_smoother → `cmd_vel`. Параметры use_sim_time переписываются верхним launch; значение True в файле само по себе не доказывает использование симуляционного времени на роботе.

**Да, Nav2 участвует в разгоне/торможении:** DWB ограничивает и прогнозирует доступные скорости по своим accel/decel; MPPI оценивает наборы будущих управляющих траекторий. Smoother отдельно ограничивает изменение выходной команды. Его OPEN_LOOP означает использование истории собственных команд при сглаживании, а не измерение физической скорости в этом слое. Наличие odom_topic в YAML не превращает OPEN_LOOP в CLOSED_LOOP. Сам controller при этом получает одометрию.

Например, переход команды 0.3 → 0 при decel 0.6 занимает около 0.5 с; при 2.5 — около 0.12 с, с квантованием таймера 20 Гц. Это длительность рампы **команды**, не физическая остановка робота. В X2 к ней добавляется собственный выбег походки. Перевод smoother в CLOSED_LOOP без проверки тоже не гарантирует улучшения: если фактическая скорость 0.45 при команде 0.12, расчёт следующего шага от измеренной скорости может дольше удерживать ненулевой выход.

## Что делает robot_driver

Проверены `gocker_go2_robot_driver` (HEAD `bbc90d1893b1837a2d94c58c245107ef5d229c7c`) и оригинальный `orig/docker_rockchip_workspace_rockchip_robot_driver`.

`src/control_interface.cpp`:

- `_cmdVelCallback` переводит vx/vy/wz в оси WirelessController через зависящие от режима коэффициенты. Для SPORT_MODE это 1.2 / 0.6 / 2.3, для AI_SPORT — 0.2 / 0.25 / 0.7. Это преобразование интерфейса, не расчёт остановочного расстояния.
- `_wCtrlLoop` вызывается каждые 100 мс (10 Гц, несмотря на старый комментарий «3 Hz»), публикует новую команду; при отсутствии новой — один ноль. В исходном checkout выход — `/wirelesscontroller_unprocessed`; последующий потребитель этого топика в проверенных исходниках backend не найден. В gocker тема задаётся параметром. Поэтому весь неизвестный downstream нельзя объявлять исследованным.
- У Go2 есть собственный контроллер походки, исполняющий такой ввод. Коэффициенты виртуальных осей нельзя переносить на SDK McLocomotionVelocity X2, где официальный пример подписывает величины как м/с и рад/с.
- В `_goalPoseCallback` есть построение полиномиального пути для `desired_pose`, но это другой callback, не цепочка Nav2 cmd_vel; в проверенном теле сформированный path не отправляется. Этот код не объясняет торможение Nav2.
- Публикация odom использует родные SportModeState velocity/position и IMU yaw-rate. В проверенной gocker реализации скорость ниже 0.1 обнуляется, а позиция масштабируется на 1.15. Эти особенности не следует копировать в X2: они вносят собственную несогласованность между позой и скоростью.

## Что проверяем на X2

Стандартная RPP-логика подхода уменьшает команду до min_approach_linear_velocity=0.12. Но прямые пробы MC показали около 0.44 м/с при 0.12, а не медленное подкрадывание. Поэтому копирование даже полностью правильных ограничений Go2 не исправляет нелинейный отклик X2 автоматически.

Добавлен исключительно SIM-параметр `QAZBOT_SIM_MC_LINEAR_DECEL` (0.1…4.0, требует изолированного MC-кандидата), обычный default не изменён. Серия `go2_braking_20261027_a` сравнивает 0.6 и 2.5 при одинаковых lead=0.8, цели 1.5 м и пределах 0.3/0.8. Alpha=0 — диагностическое отделение MC от шума модели AMCL, не конфиг робота. Проверяется истинная конечная точность, а не один статус SUCCEEDED.

## Отдельно: плавность ручного управления

Есть ещё один слой, который легко принять за поведение Nav2: `teleworker_teleop/src/teleworker_teleop_server.py`. У него собственная рампа (линейный разгон 0.4, торможение 1.0; угловой разгон 0.4, торможение 1.0), период 0.1 с, timeout 0.35 с, после выхода в ноль — один нулевой пакет и тишина. Он сглаживает собственную предыдущую команду, одометрия хранится для диагностики, а не задаёт эту рампу.

В исходном core.launch teleop принимает `/cmd_vel_not_safe`/joy и выдаёт `/cmd_vel`; Nav2 smoother выдаёт `/cmd_vel` напрямую. Следовательно, по этим исходникам teleop-рампа не стоит последовательно после Nav2. В обновлённом gocker ветви явно разделены: teleop → `/cmd_vel_teleop`, Nav2 → `/cmd_vel_nav`, primitive → `/cmd_vel_primitive`; `cmd_vel_manager` выбирает источник по приоритету/свежести и выдаёт `/cmd_vel`. В проверенном manager accel/decel-рампы нет. Отдельный `teleworker_turn_actions` тоже ограничивает рост угловой команды и уменьшает её по остаточному углу, но не является FollowPath.

Таким образом, приятное ручное управление Go2 нельзя считать доказательством того, что Nav2 предсказывает всю механику робота. Нужно сопоставлять одинаковые цепочки управления.

## Остальная навигация: что не переносить вслепую

- AMCL исходного Go2: alpha1–5=0.2 (те же defaults), OmniMotionModel, max_beams=60, update_min_d/a=0.15/0.1, likelihood_field, z_hit=0.9, likelihood_max_dist=4.0, transform_tolerance=1.0. X2 использует 1440 max_beams и base_footprint; у него другой сектор скана. Предыдущее контролируемое сравнение `amcl_accuracy_replay02` уже показало ухудшение XY p95 при 60 лучах: 37.55 против 23.60 см. Sensor model Go2 не дал убедительного выигрыша. Эти значения не выбраны defaults; отчёт `navigation_accuracy_20261026.md` сохранён.
- У Go2 local costmap — VoxelLayer, но активный observation_sources содержит **scan**; PointCloud2 описан рядом, однако не включён этим списком. Поэтому наличие VoxelLayer само по себе не доказывает свободные 3D floor rays. inf_is_valid=false; автоматическая очистка по всем inf там не включена. Это не готовое решение ghost obstacles X2.
- Геометрия исходного Go2 — footprint 0.70×0.35 м, у X2 другой габарит (радиус 0.454 м). Копирование меньшего footprint/inflation недопустимо по смыслу геометрии.
- Smac исходного Go2 допускает альтернативную конечную точку в 0.5 м от запрошенной при недоступности точной; у X2 tolerance=0.0. Это planner tolerance, не тормозной путь и не goal-checker tolerance. Успешные поездки с этими контрактами нельзя сравнивать как одинаковую точность.
- BT Go2 перестраивает путь раз в секунду, умеет ждать, очищать costmap, автоматически Spin 1.57 рад и BackUp 0.30 м. В X2 перестроение уже есть, но такие recovery-движения не копировались. Они не являются исправлением MC и требуют отдельного контракта управления.
- Исходный Go2 YAML содержит hardcoded initial_pose для своей карты; перенос этой позы в .66 был бы ошибкой. Сохранение/допуск позы X2 рассматриваются отдельно от AMCL defaults.
