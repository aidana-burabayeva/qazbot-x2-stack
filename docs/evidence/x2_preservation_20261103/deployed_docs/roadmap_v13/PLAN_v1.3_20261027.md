## 0. Результат, которого добиваемся

### 0.1. Продуктовый сценарий

Команда оператора: **«X2, подойди к столу в переговорной»**.

Система:
1. Разрешает «стол в переговорной» в безопасную **точку подхода** на версии карты офиса, а не в координату центра мебели.
2. Проверяет профиль робота, версию карты, пригодную для движения оценку позы, состояние locomotion и разрешение на навигацию; не требует произвольной «идеальной» ковариации.
3. Находит маршрут по общей 2D `OccupancyGrid` с запретными зонами и геометрией робота.
4. Управляет X2 через Nav2 → единый motion contract → AgiBot locomotion adapter → штатный контроллер ходьбы.
5. Онлайн учитывает 3D-препятствия и **не стирает объекты только из-за выхода за пределы переднего FOV**.
6. Не отступает вслепую; перед поворотом учитывает swept volume тела, ног и рук, а также неопределённость задней зоны.
7. При недостоверной локализации, отсутствии свежих критических данных, невозможности безопасного поворота или потере требуемого разрешения **останавливает выдачу новых команд и переводит задачу в явно диагностируемое состояние**.
8. По достижении цели возвращает `SUCCEEDED` **только после проверенной остановки**, вместе с фактической ошибкой, измеренной независимо. Для MVP допускается умеренная погрешность прибытия, согласованная с габаритом и свободным пространством, а не обязательные 5–10 см. При неудаче выдаётся конкретная причина.

### 0.2. Ближайшая реально достижимая версия: Navigation MVP

- X2 в цифровом двойнике проходит **из точки A в точку B по известному ровному полу** карты D1.
- Использует сохранённую карту, Nav2, локализацию на ограниченном 100–120° обзоре и локальную карту препятствий.
- Выполняет остановки, объезды, корректный разворот и отмену цели; при ошибке локализации сохраняет непрерывность **локальной одометрии**, а не маскирует скачки `map→odom`.
- Точно та же навигационная логика исполняется в симуляции и на физическом X2; сменяются *источники сенсоров* и *motion adapter*, а не алгоритм планирования.
- Нет требования к VLA/VLM, footstep planner, собственному 3D SLAM, визуальной одометрии или разработке нового RL-контроллера для первой версии. Погрешность прибытия MVP не должна оцениваться по самоподтверждающейся позе AMCL.

### 0.3. Что явно НЕ обещает MVP

- Безопасное прохождение лестниц, порогов, перепадов высоты и неизвестной поверхности.
- 360° текущую видимость: 120° не превращаются в 360° благодаря памяти.
- Корректное состояние среды за спиной после появления там нового объекта.
- Физическую устойчивость реального X2, если цифровой двойник моделирует только planar velocity, а не полноценные контакты ног.
- Универсальную работу на всех версиях AGIBOT «из одного YAML» без подтверждения SDK, датчиков и ограничений.

### 0.4. Обновление на 27.10 — раздельные причины сбоев, без подмены одной другой

**В цифровом двойнике (x86)** `random_batch01=5/8`, `random_fixed_batch01=7/8`, `random_exact_20261027_01=1/8`; последнее — инфраструктурная регрессия с T1 stale. **Корневая причина именно x86-серии пока не установлена**; нельзя приписывать её найденному позднее физическому DDS-discovery дефекту без собственного trace. `exact_goal_target3_04` прошёл разово, но не валидирует весь набор. Новые `nav2_exact_goal`, `nav2_pose_refine` и ingress candidate не production.

**На физическом X2** причиной воспроизведённых T1 bursts была upstream-задержка до Trust: при регистрации новых участников FastDDS на перегруженном 8-ядерном host FAST-LIO ограничен CPU 5–6, лишается CPU ~0.4–0.7 с, затем FAST-LIO/level_bridge догоняют очереди. Короткие T3/T4/T5 callback/eval и штатные source stamps в чистом burst не подтверждают проблему в Trust mutex. **Проверка эффекта снятия affinity ещё не выполнялась**; HAL zero-stamp — отдельный дефект. Источник стационарного дрейфа LIO связан с геометрической вырожденностью + IMU/гравитационной ошибкой; конкретный параметр bias/attitude пока не доказан.

**Правило:** исправлять сначала измеренную причину (scheduler/DDS timing или конкретный consumer), затем повторять те же сценарии. Нельзя увеличивать T1, переписывать `header.stamp`, использовать arbitrary retries или отключать Trust. Для симуляции и физического X2 сохранять разные issue IDs, baseline и cpu/runtime manifest.

## 0.5. Утверждённая локализация MVP — операторский RViz seed + AMCL на D1 + квалифицированная непрерывная odom

**Решение пользователя:** первым результатом считается физически воспроизводимая ходьба и остановка в известном офисе, а **не 5–10 см абсолютной точности**. D1 mapping готов; X2 **не строит заново** карту. Для глобального положения остаётся AMCL на D1 map v3, для которого оператор задаёт примерную позу через RViz. По мере движения, когда появляются уникальные ориентиры, AMCL может уточнять `map→odom`. Положение на однообразной стене может оставаться неоднозначным: это не блокер «улучшать AMCL вечно», но это ограничение, учитываемое в выборе первого свободного маршрута.

| Функция | MVP / следующее решение | Статус |
|---|---|---|
| Global map | оригинальная D1 `first_map` неизменна, `first_map_nav2_v3` живёт как проверенная производная | Live served = v3 PASS |
| Local odom TF | **A/B `lio` (действующий) vs `native_imu` (написанный опциональный кандидат)**. Исходный `leg_odom→lidar_imu_chest_front`; `native_imu` аккуратно даёт `odom→base_footprint` и angular rate по позам; не raw `twist.angular` | `lio` live; native code tested offline, unqualified live |
| 3D→2D scan | FAST-LIO `cloud_registered` + `level_bridge` → `/qazbot_lio/scan` со stamp источника; LIO всё ещё используется для проекции даже при `native_imu` TF-owner | работает; полезный сектор ~92° |
| Map-based correction | AMCL — единственный `map→odom`; seed от оператора RViz `2D Pose Estimate`; score/covariance наблюдать, но не требовать идеала | в стойке TF стабилен, реальная поза неоднозначна |
| Local obstacles | текущий `ObstacleLayer` только LaserScan; `PointCloud2 → VoxelLayer` **планируемый этап**, не реализованный production | TODO P5 |
| Motion | существующий Smac2D → RPP → OPEN_LOOP smoother → coordinator/adapter → AgiBot MC; физическая остановка и асимметрия не предсказаны по cmd ramp | живой control ещё не принят |
| AGIBOT builtin | лицензия модулей отсутствует (`license denied`), `loc_map_id=0`, D1 map не vendor `map_id` | **NO-GO сейчас**, не ставить условием запуска QazBot |
| Cameras | проверить RGB-D/depth streams для local obstacles, затем VIO только по необходимости | after baseline, не обязательны для MVP |

**Важный TF-инвариант:** `map→odom` AMCL и **один** `odom→base_footprint` владелец. При native-режиме level_bridge продолжает производить scan, но **не публикует TF**. Мост native-imu использует floor projection IMU (как текущий `base_footprint`), **не путать с отдельным native-to-pelvis shadow**. Миграция требует согласованности `scan.frame_id`, `TF`, `odom_topic` в AMCL/Nav2/Trust. Штатный `map→foot_contact` в глобальном `/tf_static` — потенциальная коллизия при объединении TF-графов; сохранять namespace и одноимённый `map` не смешивать.

**Что достаточно для старта:** оператор выбирает известную область в RViz, проверяет положение/ориентацию робота относительно **реальных стен/проёмов или меток**; AMCL запущен, скан согласован хотя бы с видимой геометрией, нет явной многометровой ошибки, TF и odom свежие, путь имеет достаточный clearance/тормозной запас, оператор держит RC. **Не требовать σxy <10 см или постоянного AMCL update на стойке.** `READY/MOTION_OK` при `admission_policy=go2` — операционная готовность **не доказательство** правильной pose: текущий `second_mode_weight≈0.90`, `σxy≈0.48 м`, альтернативы на метры — зафиксированное предупреждение. При движении не глушить ненужными качественными score-порогами, но реальные T1, odom reset, map mismatch и большие необъяснённые jump остаются стоп-событиями. Для старта после перезагрузки — всегда новое подтверждение; не считать сохранённую координату доказанной.

**Критерий первого MVP:** правильный маршрут по существующей карте D1 в **свободной зоне**, ровная и предсказуемая ходьба, физическая остановка и возможность отменить/перехватить; ориентир для первой 1 м пробы — **кандидат ±0.20 м и ±10° по рулетке/метке** при достаточном свободном пространстве, не глобальный продуктовый 10-см порог. Для полного офиса сначала M1/M2/M3, а не произвольные цели.

### 1.2. Какие прошлые решения сохраняем

- **Да:** D1 в роли основного картографа; карта ROS 2 OccupancyGrid в YAML/PGM с version/metadata; robot-independent Navigation API; Nav2; ROM/SDK-specific thin adapters; независимые odom/localization/costmap на каждом роботе; симуляция перед физикой.
- **Да, с оговоркой:** AMCL — базовый проверяемый кандидат для X2, а не догма. FAST-LIO — кандидат на **локальную непрерывную одометрию**, но не доказательство глобальной позы. 3D-данные могут обслуживать **локальную безопасность**, не требуя 3D-карты всего офиса.
- **Не фиксировать преждевременно:** единственный scan slice для всех задач; «только AMCL» при наблюдаемой неоднозначности; единые kinematics/turn policy для всех роботов; перенос vendor PNC-карты как обязательный путь; 2D-зрение как достаточный источник для перепадов высоты.
- **Отказаться:** искать проблемы локализации только подбором `alpha*`, таймаутов или trust threshold; объявлять любой `map→odom` скачок «фиксом» без причин; restart/reset LIO как штатный способ устранения роста памяти; безусловно доверять сохранённой позе после нового запуска; непрерывно перестраивать статическую глобальную карту во время навигации.

### 1.3. Гипотезы текущих отказов, по вероятности (пока НЕ root-cause verdict)

| Порядок | Гипотеза | Проверка / решающее наблюдение |
|---|---|---|
| H1 | Несовместимость **наблюдаемых поверхностей** 2D D1 и level-sliced 3D X2, усугублённая узким FOV | Scan-to-map overlay на одних физически соответствующих поверхностях; matched/unmatched beams по зонам и высотам; ablation между срезами. |
| H2 | Временная и кинематическая ошибка проекции: качание торса, frame extrinsics, cloud deskew, stale transform | Сравнение строго по timestamp; matched cloud при static/roll/pitch/yaw/walking; сравнение LiDAR-IMU-odom границ. |
| H3 | Недостаточная наблюдаемость в одинаковых офисных коридорах, даже при корректной геометрии | Мультигипотезные распределения позы, перестановка начальной позы, явная проверка неоднозначности; поворот в различимый участок. |
| H4 | Одометрия с discontinuity, дрейфом или неверным TF ownership | Ground-truth vs `/odom`; лог двух publisher одного TF; спайки при остановке и resume. |
| H5 | Перегрузка PC2 / очереди DDS / QoS / пропущенные события | p50/p95/p99 end-to-end delays и пропуски; повтор теста с уменьшенной некритичной нагрузкой. |
| H6 | Нарушения архитектуры в motion adapter/controller: velocity mapping, режим, приоритет, start/turn threshold | cmd velocity → vendor command → измеренная body twist, без подмены одной другой. |

**Установленная корневая причина сегодняшнего блокера:** пока **не доказана одной проверкой**. Архитектурная стратегия — отделить алгоритм Nav2 от ошибок позы/наблюдений/адаптера так, чтобы на каждом шаге был проверяемый ответ.

### 1.4. Что НЕ является причиной само по себе

- 2D-карта **не запрещает** использовать 3D LiDAR.
- FOV 120° **не означает**, что локализация физически невозможна; он повышает неоднозначность и ухудшает наблюдаемость.
- Отсутствие обновления AMCL на неподвижном роботе **не означает** автоматически устаревшую или неверную позу.
- Успех в симуляторе на perfect ground truth **не доказывает** устойчивую real-world localization.
- Наличие на X2 внутренней RL-ходьбы **не означает** поддержки автономного планирования постановки стоп на любой рельеф.

```text

               │

               ▼
  Robot Agent (per robot: local autonomous execution)
  - NavigateToPose / NavigateThroughPoses / Cancel / Status
  - local state machine, lifecycle, preflight, fail-closed
               │
   ┌───────────┴───────────────────────┐
   ▼                                   ▼
  Shared ROS 2 Nav2 stack            Perception + Localization
  map_server/static map              LiDAR/IMU/vendor odom
  planner + controller + BT           3D→2D localization observation
  global/local costmap                AMCL or validated alternative
  keepout/safety                      odom + TF with ownership
   │                                   │
   └──────────────┬────────────────────┘
                  ▼
  Common Motion Interface (Twist or TwistStamped; version-pinned)
                  ▼
  AGIBOT X2 Motion Adapter   [SIM backend | REAL vendor backend]
                  ▼

```

**Не один Nav2 на весь парк:** общий **код и API**, но *изолированная локализация, TF, obstacle memory, safety и navigation instance* для каждого робота. В multi-robot режиме исключить collisions namespace, `/tf`, `/map`, `/cmd_vel`, DDS domain и `use_sim_time`.

### 2.1. Три типа карт — не смешивать

| Представление | Источник | Назначение | Срок жизни |
|---|---|---|---|
| `OfficeMap2D` (`nav_msgs/OccupancyGrid`) | D1: карта vN | Стабильная структура здания и глобальное планирование | Фиксированная, версионированная |
| `LocalizationReference` | На MVP — валидированные 2D features/scan map; возможен отдельный 3D submap | Привязка робота к `map`; **может отличаться** для D1 и X2, но должна быть согласована геометрически | Версия привязана к `map_id` |
| `LocalObstacleMemory` (local rolling 2D/3D costmap) | Восприятие **самого** X2 | Люди, коробки, перемещённые предметы, видимые/недавно видимые поверхности | Локальная, ограниченная, со статусом наблюдения |

**Критический вывод:** 2D occupancy map D1 может остаться канонической картой для **планирования**, даже если в будущем X2 потребуется специальная 3D reference map для **локализации**. Это не «несовместимость карт», а разделение задач. Из 2D-карты офиса нельзя восстановить истинную высоту мебели/пола без дополнительных измерений.

### 2.2. TF-контракт, единственный владелец каждого ребра

```text
map ──[LOCALIZER ONLY]──> odom
odom ──[ODOMETRY AGGREGATOR ONLY]──> base_footprint  (пример)
base_footprint ──[validated body kinematics]──> base_link
base_link ──[URDF/robot_state_publisher]──> torso_link ──> lidar_chest_front
                                                  └──> cameras / IMUs
```

- Реальная топология `base_link`/`base_footprint` и динамика торса определяются **фактической кинематикой X2**. Не дублировать уже имеющиеся vendor TF и не объявлять движущийся относительно таза/ног лидар статичным.
- Никогда не публиковать два одновременно активных `map→odom` или `odom→base` для одного робота.
- Во время разработки идеальная поза симулятора может быть **отдельным управляемым источником map-frame ground truth**, но не должна одновременно конфликтовать с AMCL.
- Согласовать `map` координаты симулятора и D1 map origin, orientation, resolution; отдельный преобразователь *map↔world* не должен скрывать ошибку сдвига карты.

### 2.3. Обязательные интерфейсы

| Контракт | Пример ROS 2-типов | Условия |
|---|---|---|
| Карта | `nav_msgs/msg/OccupancyGrid` | `map_id/version`, origin/resolution/sha256, immutable during navigation |
| Локальная одометрия | `nav_msgs/msg/Odometry` + TF | Непрерывность и корректное время, covariances измерены, единственный broadcaster |
| 2D-локализация observation | `sensor_msgs/msg/LaserScan` | Только релевантный картографируемой геометрии уровень; заполняемость FOV и корректный TF |
| 3D perception | `sensor_msgs/msg/PointCloud2` / depth | Отдельный слой obstacle detection; не использовать тот же 2D-срез как единственную protection |
| Global pose | `geometry_msgs/msg/PoseWithCovarianceStamped` либо выбранный public interface | Validity = не только timestamp; интерпретация неопределённости |
| Навигация | `nav2_msgs/action/NavigateToPose` | goal/result/feedback/cancel, lifecycle, причины отказов |
| Motion | `geometry_msgs/msg/Twist` или `TwistStamped` | **Выбрать строго по зафиксированной версии Nav2**; никогда не терять timestamp silently |
| Vendor motion X2 | `/aima/mc/locomotion/velocity` (`McLocomotionVelocity`) | Регистрация `source`, приоритеты, mode, допустимые скорости и частота — по проверенной AimDK прошивке |
| Diagnostics | `diagnostic_msgs/msg/DiagnosticArray` + structured events | Источник/время/качество/причина блокировки, сквозной trace ID |

### 2.4. Безопасность и граница sim → real

- **Simulation adapter** не имеет доступа к аппаратному topic/API locomotion; physical adapter отсутствует или жёстко выключен при `mode=sim`.
- **Real adapter** включается только после отдельного явного разрешения физического теста и подтверждения приоритета пульта/оператора.
- Safety-critical feedback и остановка — **на PC2 и вендорском MC**, не на облачном сервере.
- Старые «watchdog 0.5 s» и «threshold 0.53» — исторические примеры. Новые интервалы только из measured sensor rates, worst-case timing и vendor protocol; их нельзя копировать без обоснования.
- Уход в нулевую скорость при потере локализации/сигнала — часть штатного safety state machine с bounded stopping distance; **не случайные перезапуски и retry**.
- Crash/restart/ROS graph discovery и real-time DDS — отдельный safety-gate, особенно на X2 в standing/walking mode.

## P2-T. **Два разных статуса**: x86 twin T1 OPEN; физический X2 upstream stall ROOT MECHANISM FOUND

**Новые доказательства `V2P2T` и `P2Tb` (физический X2):** трасса source→Trust через DDS `source_timestamp`, monotonic callback/eval и CPU schedstat локализовала задержку **до** Trust. **Следующий изолированный реальный A/B (только после P0-C и с контролем owner/restart):** A=`lio_cpus:=5,6` baseline; B=`lio_cpus:=` (без pin), тот же `burst_probe.py observe/sched/join` протокол bare/sub с точными временами. **Внимание:** это не доказательство причины `random_exact_20261027_01` **в x86 twin**. В нём генерация скана/odom в другом процессе и другое распределение CPU. ### P2-T.1. Точная гипотеза (в порядке проверки)

1. **Разные понятия времени**: `use_sim_time`, `/clock`, ROS timestamp, wall/monotonic time, pause/reset, разные контейнеры. Если `header.stamp` берётся раньше завершения сборки scan или clocks не согласованы, `source age` может расти, даже когда публикации регулярны.
2. **Задержка после публикации**: DDS delivery, очередь принятия или конкурентные подписчики. При publisher ~5 Гц могли задерживаться конкретные сообщения, доставляться уже устаревшими или не приниматься из-за порядка stamps.
3. **Проблема scheduling/dispatch**: контейнерный CPU pressure, callback groups, executor starvation, lock contention, таймеры; короткая *длительность самого callback* не исключает ожидания **до его вызова**.
4. **Проблема приёма и буфера Trust**: принятые source stamps, повторные/отклонённые обновления, порядок очистки очереди TF, timestamp rejection, выбор «последнего» скана и правила расчёта `age`.
5. **Нормальная фаза sampling + ошибочно выбранная модель freshness**: при 5 Гц интервал скана ≈0,2 с; надо измерить задержку от начала/конца измерения, сборки и до фактической обработки. Порог 0,5 с **не ослаблять до определения реального бюджета**.

Слабые гипотезы после неудавшихся проверок: «достаточно переключить на Reliable», «просто увеличить SHM», «один executor решит проблему», «UDP-only лучше». Это уже пробовали без устойчивого успеха; не запускать повторно без новой измеримой причины.

### P2-T.2. Диагностика: минимальный сквозной trace **одного** сообщения

На одном фиксированном seed/карте/контейнере и в тех же физических условиях наблюдать каждый скан/odom по `header.stamp` (если у потока нет sequence, коррелировать `(topic, stamp)`):

```text
T0  sensor sample ROS timestamp (в какой фазе скана выставлен)
T1  scan/odom generation done              + local steady/monotonic clock
T2  publisher.publish entered / returned  + local steady/monotonic clock
T3  Trust subscription callback ENTER      + local steady/monotonic clock
T4  stamp accepted / rejected + reason     + last accepted source stamp
T5  Trust evaluation ENTER / EXIT          + monotonic clock + ROS now
T6  verdict READY/MOTION_OK, rejection type; coordinator receives verdict
```

- На одном host использовать `time.monotonic_ns()` для **измерения интервалов локального ожидания**; ROS stamp и ROS now для **возраста измерения**. До сравнения часов разных процессов/контейнеров документировать их источник и offset; monotonic разных процессов на одном Linux host обычно сопоставим, но проверить контексты namespaces/VM и отсутствие clock jumps.
- Логировать не каждый PointCloud2: счётчики + ограниченный trace/ring buffer для событий c высоким возрастом, промежутков stamps, reject причин и фактов ожидания. Нагрузка инструмента должна быть ниже измеряемого эффекта: trace-on/trace-off A/B.
- Для scan проверить: publish gap, receive gap, `(receive_ros - stamp_ros)`, `callback_enter - publish`, `evaluate - callback`, queue residence, пропуски/дубликаты и timestamp regressions. То же отдельно для odom/TF.
- Зафиксировать runtime `use_sim_time`, `/clock`, DDS `ROS_DOMAIN_ID`, QoS endpoints, executor/callback groups, container CPU limits, IPC mode, mounts/версии двух research workers. **Сверять реально работающий процесс**, не только default YAML.
- Сравнить Trust subscriber с независимым лёгким observer на **одном и том же** topic, а не с vendor HAL иного уровня. Изменение частоты и времени допустимо только как отдельный причинный эксперимент.

### P2-T.3. Как отличить причины

| Где наблюдается первая задержка | Что исправлять |

Проверка `odom_topic` при OPEN_LOOP не делает smoother closed-loop; **не переключать CLOSED_LOOP** без реального feedback/latency A/B. Официальные понятия: https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/configuring_velocity_smoother/ (сверить параметры с Nav2 Humble 1.1.x).
- [ ] Расчёт заранее тормозного пути и допустимой погрешности основывать на измеренном отклике и неопределённости + latency локализации и препятствий; отдельно поворот на месте, движение вперед, остановка, контроль после stop. Не превращать симуляционный коэффициент в адаптерную магическую компенсацию.

**M2. Сохранить кандидаты, не активировать без доказательств:**

- `candidates/nav2_exact_goal/goal_endpoint.patch`: проверить не только шесть goal в валидной клетке и два out-of-map, но *занятую/unknown* часть целевой клетки, footprint-collision на границе и непроходимую ориентацию. Конец пути с точным XY не должен обходить collision/clearance проверки.
- `candidates/nav2_pose_refine`: удержание фазы yaw и доводка в `odom` требуют явного map-frame goal validation **после** поправки. Проверить изменение `map→odom` во время доводки, цель у стены, отмену, стоп, повторное планирование, blocked goal, отсутствие бесконечной XY↔yaw осцилляции.
- `trust_ingress` отдельный executor для TF-колбэка: сохранение восьми корректировок при mutex-hold полезно, но **не доказывает** сквозного устранения T1. Не сливать, пока нет полного rerun P2-T и safety tests.
- `AMCL likelihood_field_prob / max_beams=1440`: режим **только sim-кандидат**; `alpha=0` — лишь диагностическая изоляция, запрещён перенос на физический X2 без независимой измеренной модели ошибок.

**M3. Условия приёмки:**

1. Все 8 фиксированных целей **и возвраты**, единый манифест, **без reseed между целями** для continuous набора; истинная ошибка не больше 0,10 м / 0,10 рад в этом исследовании (текущая постановка пользователя, не общий допуск для всех гуманоидов).
2. Проверять конечную ошибку **после измеренной физической остановки сим-модели**, а не в момент `SUCCEEDED`; цель не считается пройденной при инерционном перелёте.
3. Проверить baseline vs каждый кандидат **по одному**: стабильность, распределение ошибок, velocity trace, runtime load, отказ при препятствии, отмена, регресс T1. Более строгие внутренние 0,05 м / 0,06 рад не являются доказательством конечной физической точности.
4. Нельзя автоматически выбирать MPPI/RotationShim→DWB/Go2 driver вместо RPP: это сравнение разных моделей и транспортов, а не минимальный фикс текущих X2 отказов.

**GO:** deterministic E2E без ненадёжной доставки, физическая модель настолько достоверна, насколько подтверждено экспериментом; кандидаты доказанно улучшают измеренную истинную позицию и не создают регрессий. **NO-GO:** хороший результат только на одной точке, или одна ветка исправлена ценой другой.

## P3. Сенсорная и одометрическая модель X2 без идеальных подсказок

**Цель:** представить X2 так, как он видит мир, вместо идеального всевидящего робота.

**Порядок:**

1. [ ] Смоделировать LiDAR *в его реальном ограниченном FOV*, горизонталь/вертикаль/scan rate и расположение по текущему hardware report. Если частота/угол различаются между AimDK и конкретным экземпляром — брать измеренную версию.
2. [ ] Создать raw `PointCloud2`; уровень локализации (`LaserScan`) готовить отдельно от raw 3D obstacle stream. Выбирать окно по **наблюдаемому совпадению с D1-картой**, а не переписывать исторические 0.35–1.8 м в качестве норматива.
3. [ ] Добавить roll/pitch/vertical motion торса при gait (с реалистичной амплитудой по real bags), нужные joint-state/TF и deskew-тест. Если симуляция пока planar — inject motion trajectories для processing/replay и пометить fidelity gap.
4. [ ] Предоставить sim odom с контролируемым drift, bias, yaw drift, jumps и ковариацией. Идеальную sim pose оставить только для **логирования ошибок**, а не для Nav2.
5. [ ] Ввести delay/jitter/dropouts IMU и облака из распределений **измеренных багов**, отдельно nominal и high CPU. Не добавлять случайные цифры без provenance.
6. [ ] Проверить QoS для каждого publisher/subscriber; не использовать бесконтрольный backlog sensor events.
7. [ ] Сформировать матрицу сопоставления D1 scan-height ↔ X2 projection: стена, стекло, стол на ножках, кресло, открытая дверь, человек рядом.

**GO:** измеряемые sensor mismatch и odom error; воспроизводимые облака и LaserScan, сохранившие ограниченный FOV; stable TF на движущемся торсе; отсутствие «ground truth leaks».

**Регрессия:** P2 на truth по-прежнему проходит; новые события сенсора не ломают sim clock/TF; ресурсы ограничены. **Артефакты:** `P3_sensor_fidelity.md`, набор generated/replayed bag, графики timestamps/QoS.

## P4. **Локализация X2 на готовой 2D-карте D1 — реализуем гибрид, не начинаем новый SLAM**

**Цель MVP:** X2 видит **себя на 2D-карте офиса D1**, способен пройти известный ровный маршрут и остановиться, несмотря на ограниченный передний 3D LiDAR и небольшие погрешности позы. Главное — **непрерывность**, отсутствие необъяснимых глобальных перескоков во время движения и полезная для Nav2 привязка, **не сантиметровая точность**.

**Статус 27.10:** физический `FAST-LIO → level_bridge → AMCL → Trust` работает после ручного RViz seed, D1 map v3 идентичен live карте. **Но** trial06 обнаружил неприемлемый для непрерывного odom дрейф LIO при вырожденной геометрии, тогда как native leg pose стабильна. `native_imu` реализован как **альтернативный (не default)** TF/odom-source и проходит offline/unit, live switch не выполнен. AMCL стабильность в стойке ≠ абсолютная правота: pose B в scan-map может отличаться ~1 м от лучшего локального совпадения, а сходных глобальных совпадений ≥8. Для первого MVP operator seed в RViz и визуальный осмотр стены/ориентира — достаточный стартовый процесс, но не blind `READY` от go2.

### P4.1. Карта D1 как канонический источник — **hash/served identity DONE, реальные ориентиры OPEN**

- [x] Инвентаризировать **уже построенную** карту D1; hash, origin, resolution, occupied/free/unknown semantics. Исходную карту не модифицировать; применять воспроизводимую Nav2-производную v3 или актуальную подтверждённую версию, не угадывать её по названию.
- [ ] Согласовать систему координат карты в sim и real; те же точки и ориентиры должны иметь одни и те же `map`-координаты.
- [ ] Проверить, что на карте нет ложного occupied imprint физического X2 и нет непроверенных очищенных участков. Изменение — отдельная производная версия с diff.

### P4.2. Отдельно выбранная локальная odom, один AMCL-owner, реальные фреймы

- [x] Физический `leg_odometry` ~139–168 Гц, source stamp p50 ~6 мс, `frame_id=leg_odom`, `child_frame_id=lidar_imu_chest_front`; `twist.angular=0` даже на реальном повороте 67°, поэтому копировать native `twist` нельзя.

Trial06 по native ~67.4° и ≤3.31 см XY, LIO во время последующей стойки до 1.675 м ложного перемещения. Офлайн выявлена деградация информации от передней плоской стены и горизонтальный specific-force residual ~0.18 м/с²; точный IMU bias/gravity источник **не доказан**.

В `native_imu` source stamp сохранён, одометрия и TF согласованы, source guard/JumpGuard (gap cap 0.2s → max bound 0.35 м), yaw-rate вычислен за ~0.3 с; **предпочтительный кандидат на будущий local odom, не действующий runtime**. Независимая верификация M0a c1 ещё IN PROGRESS.

В режиме stand без движения попытаться shadow variant с отдельным TF namespace. ### P4.3. Ручная начальная локализация, затем уточнение AMCL во время движения — **минимальный договор MVP**

**Доказательства 27.10:** до RViz seed AMCL не публиковал позу и TF — это корректно. Оператор послал 11 начальных гипотез, часть различалась на ~6.6 м и ~67°; последние `amcl_pose=(-1.235,-0.126,0.049)`, σx=0.403 м, σy=0.481 м, σyaw=0.264 рад, `second_mode_weight=0.903`. За 60 с на стойке `map→odom` был постоянен 5 Гц и scan age в норме, но сама по себе стабильность ничего не говорит об истинности координат. При одном текущем скане 62.2% hit10, сопоставление возможно; лучшая локальная гипотеза в 1.03 м лучше и ≥8 глобальных гипотез примерно равны. Это скорее геометрическая неоднозначность, **не доказанная ошибка высоты scan**. `go2` policy показывала `trusted=ready=motion_ok=true` при этой неоднозначности и при диагностических T2/T3/T4/T6: **не трактовать как физически проверенную позу**.

**Рабочая процедура без «душения точностью»:**
1. Оператор отмечает на D1 карте **известное физическое место X2** (рядом узнаваемая дверь/угол, ориентация по видимой стене); один `2D Pose Estimate`, не `2D Goal Pose`. Для старта не требуется 10-см измерение; но нужно исключить ошибку на несколько метров/не тот коридор. После reboot/move — всегда повторно.
2. В RViz проверить, что передний скан лежит на ожидаемых стенах и слева/справа нет явного противоречия; если есть неоднозначность, выбрать безопасный короткий маршрут к отличительному ориентиру под наблюдением, без пересечения слепой зоны. Не отправлять цель, когда оператор **не знает**, где физически стоит робот.
3. Во время движения AMCL применяет scan updates при накоплении odom motion; если сцена информативна — допускаем постепенное уточнение `map→odom`. Не требовать σxy≈0.1 м, `scan_score>0.53` в каждом тике, искусственных nomotion update или бесконечной перенастройки alpha. **Не гарантировать**, что движение вдоль одинаковой стены устраняет global ambiguity.
4. Перед стартом и на движении `T1` genuine freshness, correct map identity, timestamp monotonic, single TF owner, MC ownership и отсутствие необъяснимого скачка odom/map correction обязательны. `READY` дополняется хотя бы операторским **подтверждением начальной физической области** или измеренным независимым явным доказательством, иначе возникает silent-confident-wrong navigation. Это один подтверждающий шаг, а не отдельный SLAM проект.
5. Для раннего теста цель в широком свободном месте, достаточно clearance и выхода для остановки; принимать грубый результат (кандидат физически измеримый XY≤0.20 м / yaw≤10° для M1, позднее M3 XY≤0.25 м/15°), **не** округлять ошибки по AMCL. Если geometry/source не подтверждены — приостановить движение и запросить человеческое подтверждение.

**Ключевое разграничение:** операторский seed ≠ absolute truth; AMCL update after walk ≠ guarantee to converge. Не добавлять дополнительные глобальные локализаторы, не ждать официального AGIBOT PNC. Экспериментально подтвердить улучшение AMCL на одном информативном участке офисного маршрута и записать сравнение до/после с независимой физической точкой.

- [ ] Сначала инвентаризировать реальные встроенные RGB/RGB-D/стерео камеры X2 и доступные AimDK-топики, калибровку, экспозицию, кадры TF, загрузку Jetson; нельзя считать любую встроенную камеру готовой VIO.
- [ ] Если есть калиброванная depth/point cloud, добавить её **как второй источник local VoxelLayer** в отдельном эксперименте для препятствий ниже/сбоку, где chest LiDAR слеп. Убедиться в корректном совмещении с `odom` и отсутствии ложного clearing.
- [ ] **Visual-inertial odometry / visual place recognition** сравнивать только если есть воспроизводимые случаи, когда LiDAR-информация недостаточна при исправной сенсорной доставке, и реальная выгода превышает CPU/GPU/latency стоимость. Не запускать VIO и FAST-LIO конкурентными TF-owner.

### P4.5. Когда действительно нужна альтернатива AMCL — **не на критическом пути**

| Измеренное наблюдение | Решение |
|---|---|
| X2 удерживает грубую, но пригодную map pose на D1 и успешно проходит безопасный маршрут | **Оставить AMCL как global**; выбрать local odom (`native_imu` предпочтительно испытывать против LIO) по непрерывности, а не по названию алгоритма. |
| Проекция 3D→2D X2 не соответствует D1 по высоте/геометрии | Исправить проекцию или sensor model по одинаковым bag/test cases; не снижать score-порог как workaround. |
| FAST-LIO odom ползёт 1.675 м при стойке после поворота, native leg odom стабильна | **Проверить `native_imu` в роли odom владельца Nav2**, сохранив LIO для облаков/скана; при ухудшении откатить на `lio` и диагностировать IMU/degeneracy offline. |
| Локальный odom разрывается, сдвигается/имеет рассинхронизацию timestamp | Исправить соответствующий producer/TF/time, выполнить reset/reseed; смена AMCL не устраняет эту причину. |
| AMCL подтверждённо делает confident-wrong global jump в одинаковых коридорах при нормальных сенсорах | Сравнить multi-hypothesis map matching / альтернативный 2.5D/3D localizer, **но только после repro**, с отдельной 3D reference, связанной с D1-map. |
| Штатная AGIBOT локализация действительно работает и имеет зарегистрированную карту этого офиса | A/B shadow по независимым ориентирам; кандидат сменного global localization adapter, а не параллельный второй TF-owner. |
| Штатная AGIBOT локализация не лицензирована / нет штатной карты | Зафиксировать недоступность. **Наш D1→FAST-LIO→AMCL→Nav2 путь не блокируется**. |

### P4.6. Localization Trust — меньше ложной строгости, без обхода безопасности

Разделить **навигационную пригодность** от **оценки точности**: AMCL covariance и scan score — информативные диагностики, их пороги и связь с разрешением движения требуют эмпирической проверки в конкретном коридоре. Текущая реализация `READY/MOTION_OK` и правила T0–T8 из ранее проверенного стека не могут автоматически считаться доказательством физически точной позы. Нельзя просто снять проверки ради большего процента достижений.

**Обязательные стоп-сигналы:** действительно устаревший или неверный по timestamp поток одометрии/скана/TF, необъяснимый разрыв odom, большая и необъяснимая коррекция global frame, несовпадение identity карты, отсутствие владения MC, явная невозможность безопасной остановки/манёвра. Новая политика доверия должна быть протестирована на wrong-pose и loss cases до live-motion.

**Приёмка P4 (MVP):** локализация работает на **уже существующей карте D1**, Pose+TF ведут себя непрерывно на проверенном маршруте, небольшие смещения не ведут к бесконечным отказам, опасные скачки/ложные глобальные режимы ловятся, runtime нагрузка ограничена. **Не требуется достижение 5–10 см**. Для физического движения дополнительно требуется документированное свободное пространство и операторский допуск.

**Regression до/после:** повтор `P2-T` source→Trust, map-identity v3, stationary, forward, ±turn, similar corridor, operator occlusion, bad stamp, LIO reset, TF jump, delayed scans, map drift, vendor TF publisher appearance, recovery only after new target. Отдельно acceptance report `P4_d1_map_x2_localization_mvp.md` + bag/plot independent truth.

## P5. Динамические препятствия, память пространства, слепая зона и политика поворотов

**Цель:** X2 планирует использовать **тот же 3D LiDAR одновременно для LIO/scan-проекции и 3D local obstacle detection**; глобальная коррекция идёт через AMCL, одометрия выбирается отдельно. На переднем LiDAR ~100–120° «сейчас не видно» не означает «место пустое». Первым local perception компонентом выбран штатный Nav2 `VoxelLayer` (`PointCloud2`), не custom 3D SLAM.

### 5.1. Разделение слоёв

- **Static global map:** D1 `OccupancyGrid`; никогда не перезаписывать вслед за временным человеком/коробкой.
- **Local 3D obstacles:** `PointCloud2`/RGB-D (если моделируется и доступна на real robot), область ограничена по дальности и высоте, захватывает корпус и опасность около ног.
- **Local navigation costmap:** 2D проекция 3D-вокселей + StaticLayer/Inflation/Keepout. Использовать `VoxelLayer` из версии Nav2 как **первый** вариант; усложнять STVL/Nvblox только если обосновано сценариями и профилем CPU.
- **Observation memory:** препятствие со временем последнего достоверного наблюдения, FOV footprint, состояние «видимо / не наблюдается / ранее наблюдалось / неизвестно». Временное затухание — **модель**, не «очистка всего через N секунд».
- **Traversability / support:** в MVP только **валидированный плоский пол**; карта высот/ступени — P11. При обнаружении потенциального провала или перепада высоты — отказ в движении в область, а не гипотетическая RL-команда.

### 5.2. Как работает память при приближении

1. X2 видит коробку впереди: объект добавлен в rolling local map в `odom` frame с корректным transform на время наблюдения.
2. X2 подходит; коробка уходит ниже FOV. Она **остаётся препятствием**, пока нет законного основания её очистить (новое достоверное наблюдение *той же зоны* или обоснованная отдельная модель динамического объекта).
3. Бок/зад корпуса становится слепой зоной. Никакой raytracing «через стену / вне FOV» не снимает occupancy.
4. При достаточной неопределённости или недостаточном пространстве манёвра робот **останавливается**, а не пытается пролезть.
5. На участке, где требуется проверить неизвестную зону, сначала оценивается возможность **безопасного scan/turn**. Если это невозможно — `BLOCKED_BY_UNOBSERVED_SPACE`, не автовращение.

### 5.3. Motion policy специально для X2

- [ ] **На MVP запрещено движение назад**, кроме отдельно утверждённого recovery с дополнительным обзором.
- [ ] Отдельно определить допустимость lateral walking: штатный MC может его поддерживать, но при ограниченном обзоре боковая безопасность отдельно не доказана; default = disabled.
- [ ] Поворот допускается только после проверки **swept volume**, clearance впереди/сбоку и допустимой политики задней неизвестной области.
- [ ] Нельзя считать робот точечной базой: collision footprint + консервативный envelope при переносе ног / движении рук.
- [ ] Конфликт Nav2 Spin/BackUp recovery с политикой X2: unsafe recovery отключают **на основании capability profile**, а не обходят ошибку Nav2.
- [ ] Добавить fail-safe terminal state для «нет безопасной политики поворота»; альтернативный маршрут без движения назад.
- [ ] Не разрешать blind clearing вблизи ног: применить negative obstacle policy и отдельно проверить ложные «пол свободен».

### Acceptance metrics (политика задания чисел)

**Числовые пороги не выдумываются из воздуха.** До выполнения P6 команда фиксирует на P2–P5 измеренное распределение и требования конкретных размеров офиса:

## P9. Физическая квалификация X2 Ultra — статус V0/V1/V2/M0, затем только санкционированное движение

### P9b. Contract test движения без цели Nav2

- [ ] Под контролем оператора тестировать **короткие** команды штатному locomotion adapter на свободной поверхности: zero, small forward, yaw, комбинированное движение, stop. 
- [ ] Проверить registration `source`, приоритеты remote control, состояние stable stand/locomotion, пограничные стартовые скорости.
- [ ] Построить измеренный transfer `Nav2 requested vx/vy/wz → vendor requested → measured vx/vy/wz`; без компенсаций «на глаз».
- [ ] Если vendor MC не выполняет чистый pivot как ожидает Nav2: выбирать поддерживаемую controller/turn policy и проверять на том же симулируемом интерфейсе, а не придумывать магическое усиление `angular_velocity`.
- [ ] Проверить stop distance и control-source takeover/timeout по vendor SDK в условиях, согласованных с оператором.

### P9c. Контролируемая автономная траектория

- [ ] Navigation goal на коротком ровном свободном участке; оператор физически рядом с возможностью останова, люди удалены из тестовой зоны.
- [ ] Затем поворот, затем длиннее коридор; каждый раз log, bag, metrics и outcome.
- [ ] Независимая ground truth или верифицируемые отметки на полу; не измерять точность по самой AMCL pose.
- [ ] Повторить с изменением начальной позиции, остановкой, partial occlusion и controlled network disconnect.
- [ ] Перенести в live только те recovery, которые прошли P5/P6; не проверять blind back-up на людях.

**Physical acceptance:** отсутствие столкновений, подтверждённый локальный stop/approval, **достаточно стабильная для безопасного маршрута** оценка позы без необъяснимых прыжков, повторяемые короткие маршруты; умеренная XY/yaw ошибка допускается согласно измеренным clearance и остановочному пути; каждое числовое performance условие — из согласованного metrics spec. **Исключить** лестницы, провалы и движущиеся толпы из первого релиза.

**GO:** `P9_real_x2_acceptance.md`, логи, перечень допущенных эксплуатационных зон, карта и профили зафиксированы. **NO-GO:** реальный алгоритм использует непроверенную симуляционную модель или лишает оператора управления.

## P10. Второй робот D1: доказать универсальность, а не имитировать её

**Цель:** общий backend и общая карта обслуживают **две аппаратно разные платформы** при собственных экземплярах localization/Nav2/safety/motion.

1. [ ] На профиль D1 назначить его уже существующий 2D LiDAR/odom/motion adapter; строго сохранить эксклюзивный доступ к UART/SDK, установленный в прежних аудитах.
2. [ ] Использовать **тот же `map_id/version`**, но другой sensor observation model, footprint и velocity limits.
3. [ ] Сравнить localization/start/restart на D1 и X2 на 3–5 общих маршрутах с одинаковыми целевыми **координатами карты**, а не одинаковыми raw scan или скоростями.
4. [ ] Два робот-агента в отдельных namespaces/DDS graph и изолированными `/tf`, локальными costmap, error reasons, command channels.
5. [ ] Проверить операции backend `navigate/cancel/status/get_pose` без knowledge of vendor message type.
6. [ ] Включить версионирование map updates: одна карта распространяется на обоих с проверкой hashes, каждый robot подтверждает переключение **только вне активной задачи**.
7. [ ] Проверить, что D1 может создавать новую версию карты офлайн, а X2 использует утверждённую immutable версию; локальный Nav2 не запускает mapping при обычной навигации.

**GO:** оба робота проходят принятый набор маршрутов в своих валидированных условиях, backend не содержит hardcoded `if robot == x2` в бизнес-логике кроме выборки capability profile. **NO-GO:** глобальная TF или motion-command collision между роботами.

**Замечание:** если парк D1 включает колёсные и шагающие ревизии, **каждая ревизия требует собственного validated locomotion profile**. Одна марка D1 не равна одному controller.

## P11. После MVP: карта высот, сложный рельеф, семантика и другие AGIBOT

### P11a. Terrain awareness / зона опоры

- Проверить наличие и качество vendor `/perception/grid_map`, obstacle semantic/polygon на **вашей** firmware и SDK; не считать опциональный модуль доступным по умолчанию.
- Если grid_map доступна: привязка к `odom`/body frames, extrinsics, freshness, confidence и физическая проверка по тестовым плоским/наклонным сценам.
- Если grid_map нет: отдельная offline оценка RGB-D/3D LiDAR elevation pipeline на Jetson (или в DGX для исследований); разработка локального traversability map только по измеренному gap.
- Разделить **terrain perception** и **terrain control**. Карта высот не даёт права Nav2 выдавать команду ходьбы на ступень; требуется доказанный интерфейс vendor locomotion для выбора опоры или отдельная сертифицированная исследовательская ветка whole-body control.
- Пока vendor RL не поддерживает описанную задачу, лестницы остаются **недопустимой зоной**. Не подменять постановку стоп `cmd_vel` в зоне провала.

### P11b. Семантика «подойди к столу»

- Сначала deterministic named POIs + approach poses, доступные и проверяемые оператором.
- Затем RGB-D object association (стол/дверь) и локальная актуализация safe approach pose, с проверкой коллизии.
- VLM/VLA может работать **на сервере** только как high-level interpreter; результат — структурированная цель/план и проверка допустимости локальным robot agent.
- Никогда не преобразовывать свободный текст нейросети непосредственно в vendor joint/motion command.

### P11c. Поддержка X2/A2/A3/G2/D1 Pro/Ultra/Max/Max Pro/C5

Для каждой модели создать `capability.yaml` **после** подтверждения SDK конкретной версии:

| Аспект | Вопрос к документации/железу |
|---|---|
| Motion | Velocity API? режим locomotion? приоритеты источников? допустимый yaw/pivot? обратный ход? |
| Sensors | Какие LiDAR/camera/IMU/force streams реально доступны с timestamp/TF? |
| Localization | Есть ли пригодный vendor pose, собственный 2D/3D localizer, ограничение обзора? |
| Kinematics | Footprint, upper-body sweep, максимальная скорость, торможение, способы разворота? |
| CPU/GPU | Jetson/PC separation, невмешательство в MC, запас при штатной работе? |
| Safety | E-stop/pult, remote arbitration, network loss policy, для кого ответственность за fall avoidance? |
| Sim | Есть ли физически корректный digital twin или только proxy? |

**Не делаем портирование только ради количества профилей.** Следующую модель вводим после двух успешных подтверждённых платформ и наличия её реального владельца/испытательной площадки.

## 4. Технические решения, которые должны быть зафиксированы как ADR

| ADR | Решение | Причина | Можно пересмотреть, если... |
|---|---|---|---|
| A01 | ROS 2/Nav2 остаётся внутренним навигационным стандартом | Уже есть код, реплеи, практика D1/X2; доступна экосистема | Nav2 не выполняет измеримое критическое требование и нет корректной конфигурации/plugin |
| A02 | D1 создаёт **каноническую 2D карту**, X2 пользуется ею | Повторное картирование X2 не нужно для глобального маршрута | D1 не даёт требуемой геометрии; тогда улучшать reference (например 3D), не отказываться от 2D для планирования |
| A03 | Nav2 и safety живут локально | Control loop, sensor latency, потеря сети | Не пересматриваем ради экономии CPU; оптимизируем локальную нагрузку |
| A04 | Vendor RL/motor control — black box | Не нужно управлять суставами для flat-floor MVP | Появляется обоснованная задача terrain footstep control и договорённый interface |
| A05 | Один TF publisher на ребро | Дубли TF создают неопределённую позу | Не пересматриваем |
| A06 | Global map в навигации frozen/immutable | Избежать постоянного роста карты и непредсказуемого изменения пути | Отдельно спроектировано controlled map-update с транзакцией версии |
| A07 | 2D scan — **локализационное представление**, raw 3D — obstacle representation | Scan-height D1/X2 mismatch, опасность терять низкие/высокие объекты | Измерения показывают безопасный общий representation |
| A08 | AMCL — baseline + explicit A/B fallback | Минимальный стандартный стек, измеренная альтернатива при провале | Коридоры дают confident-wrong poses после корректного time/TF/preprocessing |
| A09 | В sim сначала truth, потом localization | Разделение неисправностей; контролируемый experimental design | Не пересматриваем |
| A10 | Существующий `control_backend` — основа | Не дублировать API, бизнес-логику, авторизацию, хранение | Подтверждён технический критический дефект, документированный ADR migration |
| A11 | Robot profile — capabilities, не просто remap topics | Разные ревизии, FOV, ограничения ходьбы и протоколы | Не пересматриваем |
| A12 | Fail-closed + запрет blind reverse в X2 MVP | Ограниченный передний FOV, неопределённость за роботом | Дополнительные сенсоры и пройденная safety verification |

### 4.1. Критические инженерные различия

**Localization vs local odometry.** FAST-LIO/leg odom может быть локально непрерывной и при этом глобально смещённой; `map→odom` определяется localizer и не должен скрывать discontinuities. При восстановлении LIO новый origin сессии нельзя безусловно приравнивать прошлому.

**Map vs 3D obstacle memory.** Карта D1 описывает стены/свободные участки на уровне картографа. Объект «исчез» из LiDAR — это недостаток текущей видимости, а не доказательство свободного пространства. Memory bounded и наблюдаемо очищается.

**Planner vs locomotion.** Nav2 выбирает путь/velocity, vendor RL обеспечивает gait. Если нижний контроллер не выполняет запрошенный pivot, вопрос может быть в модели движений, а не только в коэффициентах Nav2.

**Simulation proxy vs humanoid digital twin.** Planar proxy валидирует routing, costmaps, ROS actions, feedback, safety policy, но не проверяет реальную фазу шага, floor contact и падения.

**Control backend vs robot agent.** Backend работает с задачами и картами, а local agent — с последним метрически точным pose/obstacle/motion. Отказ Wi-Fi не должен лишать робота способности безопасно остановиться.

## 5. Ресурсы PC2, CPU/GPU и сеть

### 5.1. Правило размещения

| Задача | Назначение | Комментарий |
|---|---|---|
| Vendor MC / RL / joint safety | Вендорский motion controller X2, без вмешательства | Не запускать пользовательские тяжёлые процессы там, где это запрещено AGIBOT |
| Raw LiDAR/IMU ingest, timestamp normalization, local odom | PC2 X2 | Критична задержка; минимальные копирования PointCloud2 |
| AMCL/принятый localizer, TF, Nav2 controller/local costmap, fail-safe | PC2 X2 | Робот должен работать автономно при потере сервера |
| Global path planning | На PC2 на MVP | Возможно локальный cache / periodic rebuild; не делать удалённым критичным |
| Map serving | Локальный versioned copy + серверный registry | Map hash проверяется до запуска Nav2 |
| Семантические команды, модели распознавания, аналитика, batch simulation | Сервер/DGX при наличии | Асинхронно; у робота остаётся последний безопасный план |
| Обработка больших rosbag, comparison benchmarks, обучение модели | Сервер/workstation | Offline job, без control loop |

### 5.2. Не лечить перегрузку отключением проверок

- [ ] Собрать per-node CPU/RSS, GPU, queue depth, end-to-end freshness latency, DDS discovery и пропуски на baseline.
- [ ] Убрать **дублирующую** обработку облака и подписки, если они обрабатывают те же данные без полезного различия.
- [ ] Downsample/range crop/ROI только по *accuracy-vs-resource* испытанию; сохранить низкие препятствия и полезные для AMCL стены.
- [ ] Ограничивать `rolling_window` local map измеренным радиусом торможения, sensor range и скоростью; не «минимальным для CPU».
- [ ] QoS выбирать по publisher/subscriber контракту (`ros2 topic info -v`), backlog не должен превращать данные прошлого в «новые».
- [ ] При загрузке CPU проверять рост p99 latency, а не только средний %; резерв для motion/SLAM сенсоров обязателен.
- [ ] Если доступна vendor `/perception/grid_map`, измерить её real CPU cost и latency; не принимать без валидации качества.

### 5.3. Сеть и сервер

- [ ] Разделить control plane (задание, статус, отмена, карты) от ROS-local data plane (high-rate sensors/motion).
- [ ] Никакого потокового LiDAR на backend по Wi-Fi в critical loop; использовать локальную обработку и отдельный selected telemetry stream.
- [ ] Сверить версию карты локально и серверно, checksum и atomic activate вне active goal.
- [ ] Задать локальную реакцию на backend disconnection по классам задач, с explicit cancellation semantics.
- [ ] В multi-robot тестах проверить namespacing, QoS/ROS_DOMAIN_ID, доступность discovery без влияния на MC.
- [ ] SSL/authz/roles: удалённая команда физического движения доступна только авторизованному клиенту и локально допущенному состоянию робота.

## 6. Обязательный regression framework (сразу с P0)

### 6.1. До/после каждого изменения

**Перед изменением:**

1. Зафиксировать `commit/hash`, map/profile hash, ROS/Nav2/SDK versions, sim seed, replay bag hashes.
2. Запустить весь существующий набор unit/integration/e2e (включая старые известные failing tests с отдельным issue ID; не маскировать ошибки).
3. Записать ключевые метрики poses/commands/costmaps/CPU/RAM/latency/goal outcomes.
4. Явно записать одну проверяемую root cause гипотезу; изменить **одну ответственную переменную/компонент**.

**После изменения:**

1. Перезапустить те же seeds, bags, маршруты и invalid input cases.
2. Подтвердить, что исправлена **конкретная причина**, а не только исчезло сообщение лога.
3. Сверить trajectory/clearance, TF owner, stamped sensor ages, memory slope, CPU p99, ошибку global pose, latency/false confidence.
4. Сохранить before/after отчёт с diff и объяснением любых новых отклонений.
5. Если появился отрицательный regression — revert и новый ADR, не включать «временную заплатку».

### 6.3. Для известного blocker «робот плохо поворачивается»

До фикса обязателен **трёхступенчатый тест**:

1. **Идеальная поза + Nav2 + sim adapter:** `requested angular_velocity`, траектория, какие recovery выбирает Nav2.
2. **Sim vendor characteristics:** команда выше/ниже реального threshold, step-start behavior, ограничения yaw/lateral, resulting trajectory.
3. **Physical supervised test:** `actual yaw(t)`, ошибочная ориентация, задержка старта, ошибка измерения; только после safety gate.

Если в шаге (1) поворот правильный, а в (2)/(3) нет — искать cause в калибровке контракта, mode/start thresholds или ограничениях MC, а не пересобирать global planner. Если ошибка уже в (1) — отладить Nav2/controller profile. Если в (1) и (2) всё хорошо, а после добавления AMCL начинает «гулять» yaw — локализация/TF проблема.

## 9. Стоп-условия и риски по всей системе

| Риск | Затронутые части | Обязательное противодействие / проверка |
|---|---|---|
| Уверенно неверная pose | localizer, global planner, motion | Independent truth on sim; lost confidence = no motion; test repeated corridors |
| TF double-publisher или неправильные штампы | all ROS consumers | TF owner contract + timestamped tf2 lookups + no second map→odom |
| Неверная высота 2D-среза | D1 map ↔ X2 LiDAR | matched surfaces test по высоте; 3D obstacles отдельным потоком |
| Пропажа объекта из FOV | local costmap/safety | no blind clearing, observed-space reasoning, memory bounded |
| Непроверенная опора для стопы | locomotion/fall safety | flat-only geofence, unknown floor = no-go |
| MC не исполняет pivot/малую скорость | motion adapter, Nav2 recovery | measured requested/executed turn, vendor mode/source arbitration |
| CPU/RAM рост и тайминг | PC2, DDS, LIO, localization | per-process profiling, no redundant subscriptions, bounded structures, p99 latency |
| Потеря сети/двойная задача | backend, agent | local safety, goal idempotency, atomic task state, structured failure |
| Смена карты между задачей и localizer | map server/backend | immutable map hash/version and atomic activate |
| Избыточная вера в симуляцию | release process | P8 real bag replay → P9 controlled physical tests; documented fidelity gaps |
| Поломка пульта/MC при развёртывании | vendor/runtime safety | explicit approvals, no modification of vendor protected configs, rollback |

**Чем доказывается отсутствие регрессий:** воспроизводимыми тестами T01–T34 + сравнением численных метрик P0/P2/P4/P6/P8. До выполнения этих проверок финальная фраза «устраняет корневую причину и не создаёт регрессий» **недопустима**.

## 11. Финальный инженерный вердикт (27.10.2026, v1.3)

**Что принято:** D1 карта офиса → AMCL как единственный global `map→odom` с **ручным начальным RViz seed и последующим уточнением по ходу**, без обязательной 10-см точности; local odom **выбирается** между действующим LIO и уже реализованным `native_imu` после shadow+TF verification (native перспективнее по исходным физическим измерениям). FAST-LIO сохраняется для обработки 3D облаков и виртуального scan. Для local препятствий только планируемый PointCloud2/VoxelLayer; камеры полезны далее, но не блокируют проход A→B.

**Новая физическая root-cause картина:** три независимых проблемы, не одна — (1) T1 staleness при FastDDS discovery contention + LIO CPU affinity, (2) LIO false translation при вырожденной planar геометрии и IMU residual, (3) ошибочная/неоднозначная глобальная hypothesis при ограниченном FOV, которую go2 READY не исключает. Подтверждены **механизмы (1–2)** и scan ambiguity (3); **эффект CPU-fix, точный IMU bias и физическая absolute pose не подтверждены**. Состояние x86 twin T1 по-прежнему отдельная непроверенная root cause.

**Код уже разработан:** native-to-pelvis shadow + `native_imu` bridge и источник через launch, stop limiter в S3 после NaN-fix; source→Trust наблюдатели и DDS/scheduler trace; частичная проверка map/twin. Не выдавать их наличие в файлах за применение к Nav2/runtime или физическую приёмку. `candidates` и `ws/src/navigation` имели неатрибутированное копирование; это обязательный release blocker до рестарта/движения.

**Как двигаемся, не «душа» робот точностью:** один операторский ввод RViz в узнаваемой части офиса, один физический ориентир, свободная площадка, 1 м ходьбы → поворот → A→B; измеряем остановку, исключаем скачки/просрочку/MC takeover. Улучшать `AMCL alpha`, NDT, VIO и vendor PNC только при конкретной невозможности такого сценария с записанным proof. Симулятор независимо возвращает воспроизводимый E2E и 3D obstacle tests.

**Вердикт по отсутствию регрессий:** **пока НЕ ГОТОВО**. Не пройдены независимая верификация M0a, полный `tests/loc_trust` (legacy failures), запуск unpinned A/B, x86 T1 trace, физическая проверка S4 takeover и M1/M2/M3, проверка physical map↔office landmarks и восстановления повреждённых файлов. Поэтому нельзя утверждать, что все решения устранили корневые причины и не создали регрессий. Следующий инженерный результат — воспроизводимый, управляемый 1-метровый проход X2 с корректным остановом на D1-карте.
