# Управление поворотом и параллельные испытания — 26.10.2026

В официальном MC v1.0.0 получен рабочий SIM-кандидат управления углом. Это не установка на .66 и не закрытие всей навигации: MC робота другой версии, обычный профиль AMCL и линейный перелёт остаются отдельными проблемами.

## Что изменено

Команда 0.5 рад/с затухала; постоянные ±0.8 поддерживали шагание, но фактическая скорость превышала заданную. Поэтому кандидат управляет измеренным углом: подаёт ±0.8, заранее обнуляет команду по измеренной угловой скорости (lead 0.20 с), ждёт остановки не менее 3 с и при необходимости выполняет ограниченные коррекции. Максимум четыре попытки; бесконечного вращения нет.

`tools/twin/mc_turn_controller` реализует отдельный Nav2 plugin поверх штатного RPP. Обычное движение остаётся у RPP, поворот использует обратную связь и проверку столкновений для фактически выбранной команды. PoseProgressChecker учитывает угловой прогресс; таймаут 15 с сохранён. GoalChecker требует остановки и 3 с непрерывного допуска. Обновление пути к той же цели не сбрасывает выдержку; смена цели, выход из допуска и разрыв наблюдений сбрасывают её. Это существенно, поскольку [Nav2 сбрасывает goal checker при установке обновлённого пути](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_controller/src/controller_server.cpp).

Кандидат включается только через `QAZBOT_SIM_MC_TURN=1`, с проверками SIM/domain 87/localhost. Обычный запуск и предел 0.5 не переключены. Для кандидата ускорено только обнуление угловой команды; линейные ограничения сохранены. Сборка: `tools/twin/docker/build_turn_controller.sh`.

## Параллельный стенд

`tools/twin/parallel_turn_sweep.py` запускает два независимых MC+MuJoCo worker. У каждого собственные изменяемые конфиги, логи, IPC и CPU-набор; Docker network=none, общие vendor assets доступны только для чтения. Параметры и порядок случаев сохраняются в manifest. Результат пишется атомарно; `--resume` сохраняет завершённые измерения, включая неудачные.

Два worker выбраны под текущие CPU и одновременные задачи. Сотни официальных MC на этом компьютере не помещаются по вычислительной нагрузке. Это очередь полноценных экземпляров, без векторизации физики и ускорения времени RL. Real-time factor не измерен; состояние между случаями одного worker наследуется после нормализующей ходьбы/остановки, поэтому случаи не являются полностью независимыми рестартами.

Пример повторения финальной серии с новым именем:

```bash
python3 tools/twin/parallel_turn_sweep.py \
  --name turn_grid_repeat --lead-times 0.20 \
  --angles -180 -90 -30 30 90 180 --repeats 2 \
  --tolerance 0.08 --turn-seconds 16 \
  --adaptive-finish --adapter-zero-burst \
  --scratch-root /dev/shm/qazbot-turn-sweeps
```

В D протокол остановки соответствует адаптеру: пять нулевых пакетов, затем тишина. Оценка через 6 с после завершения, а не через произвольный остаток фиксированного окна. Предельные результаты D:

- Ошибка таза: **5.374°**, допуск 0.1 рад (5.73°).
- Ошибка лодыжки относительно заданного угла: **7.542°**, диагностический предел 10°.
- Максимальное смещение таза при повороте: **0.0959 м**, диагностический предел 0.15 м.
- Все случаи без MC abort, потери телеметрии или пропущенных результатов.

Архивы C/D имеют `ARCHIVE_COMPLETE`; `summary.json`, `manifest.json`, `case_*/data.npz` сохраняют измерения. График всех завершённых серий: `logs/twin/turn_grid_20261026_d/angle_errors.png`. Сводка A/C сохранена с первоначальной методикой, не пересчитана для улучшения результата.

## Настоящий Nav2 → адаптер → официальный MC

Два roundtrip с поворотной целью от фактической стартовой позы завершились: **4/4 цели SUCCEEDED**, точность проверена по истине MuJoCo. Явные допуски — 0.10 м / 0.10 рад.

| `tests/integration_results/` | Цель | Ошибка туда, м / рад | Ошибка обратно, м / рад |
|---|---|---|---|
| `mc_turn_nav_angle06` | +90° | 0.01437 / 0.06647 | 0.01545 / 0.04680 |
| `mc_turn_nav_angle07` | -180° | 0.06458 / 0.04246 | 0.08753 / 0.05019 |

`turn_frame_audit.json` в каждом каталоге проверяет HAL-таз и согласованные по исходному времени TF груди/лодыжек. Ошибок восстановления TF нет. В angle06 туда таз/грудь/левая/правая лодыжка повернулись на 93.91/93.77/94.54/93.78°; в angle07 туда — на 177.39/177.52/178.09/176.67°. Следовательно, поворачивается вся опора, а не только корпус.

**Ограничение этих двух успешных тестов:** `--amcl-motion-noise 0` отключал alpha1–5 только для диагностического случая с истинной одометрией симулятора. Это не параметры для робота и не новый default. С обычным AMCL наблюдались ошибки оценённой XY порядка 0.1–0.15 м и остановка `goal_alignment_not_converging`; неудачные angle01/02/04/05 сохранены. Первые прогоны также выявили и помогли исправить переключение режима финального поворота и сброс выдержки при обновлении пути.

Текущие более строгие GUI defaults 0.05 м / 0.06 рад этими результатами не квалифицированы. Полный маршрут 1.5 м `mc_turn_nav_route01` **не прошёл**: перелёт около 0.214 м и последующая неудачная доводка. Блокер линейного подхода остаётся.

## Проверки и границы вывода

Локально: 7 целевых unit-тестов прошли, модуль launch пропущен из-за отсутствия ROS launch на хосте; отдельный запуск в ROS-контейнере ранее подтвердил launch guards вместе с регулятором (7 passed). C++ plugin собран и загружен в успешных интеграционных тестах. Проверки Python-синтаксиса и bash -n прошли. Проверяются ограничение попыток, торможение по измеренной скорости, выдержка при обновлениях пути, изоляция конфигов и атомарность результатов.

После серии собственные измерительные контейнеры остановлены. Чужие параллельные задачи и .66 не изменены. Результат — проверенный на перечисленных SIM-случаях кандидат; перенос на MC v1.1.0-r9-rc9 и реальную одометрию требует отдельной проверки. Перед каждым физическим движением сохраняется требование пользователя: объявить пробу и дождаться «да/готово».
