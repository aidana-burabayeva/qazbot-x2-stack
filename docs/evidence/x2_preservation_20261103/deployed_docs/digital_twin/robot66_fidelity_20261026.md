# Приближение twin к .66: изменения и проверка 26.10.2026

**Статус: физический двойник .66 пока НЕ квалифицирован.** Добавлены проверяемый профиль наблюдений, вариант физической модели по снимку .66 и количественная проверка соответствия. Перенос настроек движения на робота по этим результатам не обоснован. Робот не изменялся; SSH при проверке — No route to host. Все движения происходили в контейнере network=none, домен 87.

**Уточнение запуска 26.10:** обнаружено, что vendor `start_sim.sh -s -c PATH` после разбора `-c` удаляет выбранную конфигурацию и может запускать исходную сцену. В `inside_sim.sh` для overlay теперь используется только `-c`; для исходной модели — `-s`. Поэтому прежние динамические сравнения ниже, не подтверждённые фактическим `--cfg_file_path` процесса симулятора, требуют повторного прогона. Создание overlay и офлайн-проверка массы сохраняют силу; прежние числа движения нельзя использовать как доказанное сравнение двух физических моделей. Интерактивный запуск теперь проверяет путь конфигурации работающего процесса.

## Что улучшено

`QAZBOT_SENSOR_PROFILE=robot66` выбирает новый `tools/twin/robot66_plant_bridge.py`; прежний `ideal` сохранён отдельно. Новый bridge:

- Отделяет истину таза (`model_truth`, child pelvis) от виртуальной точки наблюдения на груди (`model_observation_truth`) и задержанной одометрии/TF для Nav2.
- Соединяет HAL-позу таза с vendor FK `pelvis -> lidar_chest_front` **на тот же source timestamp**, затем использует .66 extrinsic из `ws/src/lio/x2.yaml`, чтобы получить точку LiDAR IMU. Направление движения определяется проекцией оси LiDAR, как в level_bridge. При отсутствии FK наблюдение пропускается, подмены тазом нет.
- Использует профиль, извлечённый из `g_motion_02/03`: одометрия около 10 Гц, скан около 5 Гц, 1440 бинов, range_min 0,45 м, range_max 8 м, медианный receive−header lag одометрии 45 мс. Точка отсчёта и расчёт скорости по окну 0,3 с воспроизводят структуру level_bridge.
- Скан ограничен приблизительным сектором 103° из описания .66 в x2.yaml. Ненаблюдаемые направления остаются inf. Фактическая форма 3D-проекции не объявляется воспроизведённой.
- Сохраняет исходные timestamps: не выдаёт замершую позу за свежую. Для шага времени назад очищает накопленные наблюдения/скорость. Публикует профиль, возраст и счётчик пропущенных FK в `twin/status`.

`tools/twin/extract_sensor_profile.py` читает закрытые bag только read-only, сохраняет происхождение, hash metadata, измеренные распределения и extrinsic. `tools/twin/profiles/robot66_observation_v1.json` — **профиль сохранённых записей, не проверка текущих настроек включённого робота**. Записи имеют range_max 8 м. Хотя default внутри level_bridge равен 25 м, production localization.launch.py явно задаёт range_max:=8.0 и scan_every:=2 — именно эти эффективные параметры воспроизведены.

Пассивный интеграционный контроль (`check_observation_profile.py`) прошёл 7 проверок: скан 4,75 Гц, odom 9,74 Гц, медианный возраст 47,6 мс, смещение груди относительно таза 0,109 м, 1440 бинов, вне сектора конечных лучей нет. Это контроль структуры и таймингов, не полного сенсорного соответствия.

**Известный остаточный разрыв:** в данной сцене доля конечных лучей 0,285 против медианы 0,097 в исходных bag. 2D ray-cast не воспроизводит вертикальный срез, разреженность облака и фильтрацию пола. Вероятности конечных лучей сохранены для анализа, но не превращены автоматически в «калиброванный dropout»: они зависят от сцены. Нет LIO-дрейфа, raw-cloud/IMU FAST-LIO, сенсорного шума, физических стен карты. Это существенные ограничения для AMCL.

## Физическая модель по URDF .66

`tools/twin/make_robot66_model.py` создаёт независимый overlay из `vendor/pc1_mc/pc1_mc_param_r9-rc3/urdf/x2_31dof_hand.urdf`. Перед переносом инерций проверяются локальные координаты тел. Массы неподвижных сенсоров и других fixed links сворачиваются в соответствующее тело с переносом центра масс и теоремой Штейнера; потерянные и повторно учтённые inertials запрещены. MC, политика, контакты, трение и ограничения приводов не подгоняются.

Полученный вариант: `runtime_x86/twin_robot66/configuration`. Исходные vendor-файлы не менялись. Для проверки компиляции установлен отдельный venv `runtime_x86/twin_tools_venv` с MuJoCo **3.3.7**, совпадающим с версией libmujoco.so официального simulator.

| Скомпилированная модель | Полная масса | Масса таза |
|---|---:|---:|
| официальный XML | 43,475 кг | 5,032 кг |
| overlay номинальной URDF .66 | 41,628 кг | 3,185 кг |

Это номинальные параметры модели, **не взвешивание реального робота**. В старом XML масса таза выводилась MuJoCo из collision mesh; простое суммирование явных inertial дало бы неверный ответ. Оба скомпилированных варианта имеют nq=38, nu=31. Overlay запущен с официальным MC и устойчиво стоял (body=1, fsm=4, z≈0,653 м).

Выбор для опыта: `QAZBOT_TWIN_MODEL=robot66_nominal`; default остаётся `official`, поскольку overlay не прошёл проверку динамики ниже. Файлы mesh и конфигурации связаны относительными symlinks, работают и на host, и в контейнере. Получить/собрать overlay заново можно командой:

```bash
python3 tools/twin/make_robot66_model.py \
  vendor/official/sim/sim_mujoco-x86-v1.0.0-20260522/configuration/robot/lx2501_3_t2d5 \
  vendor/pc1_mc/pc1_mc_param_r9-rc3/urdf/x2_31dof_hand.urdf \
  runtime_x86/twin_robot66/configuration
```

Существующий output намеренно не перезаписывается.

## Сравнение с реальным телом, без подгонки коэффициентов

`make_body_references.py` упаковал две существующие аппаратные пробы: `trial05` (development) и `trial06` (holdout относительно построения модели/профиля). Исходные JSON и их SHA256 сохранены. Опорный сигнал — штатная leg_odometry, преобразованная по vendor TF в base_link; **это независимый от LIO прокси, а не внешняя истина**. В реальности между этими пробами убрали стульчик; совпадение начальной стойки/контакта не обеспечено. Сравнение может опровергнуть соответствие, но не доказать причину расхождения.

В sim повторены амплитуда и длительность: +0,5 рад/с на 20,050 с и 5,868 с; источник SDK priority 30, timeout 1000, 50 Гц, 2 с нулей до и 6 с после. Это прямой MC boundary probe, без адаптера/Trust/Nav2. Порядок фиксирован, внутри пары полного рестарта нет. Для каждого варианта модели перед парой была нормализована стойка; это по одному наблюдению, не независимая статистика.

`assess_body_match.py` отказывается сравнивать разные команды, снимает различие начальных мировых координат и heading, сохраняет полный unwrap поворота, сравнивает траекторию и конечную позу через 3 с после нуля. Предварительные диагностические границы заданы в коде до сравнения: 5° по yaw и 5 см по XY; они не являются требованиями безопасности или гарантией пригодности.

| Проба | Реальный конечный yaw | Официальный XML | Overlay URDF .66 |
|---|---:|---:|---:|
| trial05 | +0,26° | +3,57° | +19,32° |
| trial06 | +67,43° | −2,92° | −1,67° |

Официальная модель приблизила trial05, но ошиблась на trial06 на **70,35°**. Overlay ошибся на **69,10°**, а trial05 ухудшил. Он **не принят как основная модель**. В обоих случаях `physically_validated=false`; положительный исход одной пробы не повышает этот статус автоматически. Данные и график: `logs/twin/qualification_20261026/{trial*_comparison.json,body_validation.png,compiled_models.json}`.

Такой разрыв нельзя исправлять одним gain: реальные два исхода на +0,5 существенно различаются. Нужны совпадающие начальные состояния/история, повторы и данные о физических контактах, а также устранение различия MC. Подгонять массу/трение по конечному углу единственной пробы было бы переобучением.

## Сквозная проверка нового наблюдателя

Запуск:

```bash
QAZBOT_TWIN_MODEL=official QAZBOT_SENSOR_PROFILE=robot66 \
QAZBOT_TRUST_POLICY=go2 QAZBOT_MAX_ANGULAR=0.5 \
  tools/twin/docker/run_official_chain.sh UNIQUE_RESULT_NAME
```

Harness записывает модель, профиль и политику. AMCL seed ставится в истинную точку **наблюдателя груди**, а не таза. Ошибка AMCL сравнивается с ближайшим truth sample по source timestamp (пары дальше 150 мс отвергаются). Для цели отдельно сохраняются ошибка виртуальной точки и ошибка тела; смещение груди больше не смешивается с перелётом таза.

Первый `off_robot66_profile_01`: цель туда SUCCEEDED, но истинная ошибка наблюдателя 0,242 м, тела 0,143 м; обратно ABORTED. Все пять дочерних процессов штатно завершились code=0. Записаны 9 AMCL updates, и старая жёсткая проверка `n>=10` завершила harness AssertionError уже после измерений. Результат не скрыт. Теперь в official-опытах недостаток AMCL samples сохраняется как провал диагностической проверки (`hard=false`), аналогично измерительным проверкам целей; автоматического объявления точности по малой выборке нет. Повтор `off_robot66_profile_02` с этой поправкой завершился rc=0: туда SUCCEEDED, истинная ошибка груди 0,238 м, тела 0,142 м; обратно ABORTED / Failed to make progress. 12 AMCL updates, timestamp-matched p95 XY=0,055 м, yaw=0,031 рад. Все дочерние процессы code=0. Границы команд соблюдены (959 пакетов), Trust/Coordinator faults нет. Это повтор дефекта, а не успешная навигация.

## Поиск более подходящего MC

Проверено 26.10.2026:

- Официальный [список загрузок AimDK](https://x2-aimdk.agibot.com/sdk-downloads.json), используемый тулбаром сайта, публикует mc-x86 и sim_mujoco-x86 **v1.0.0-20260522**. Это наши имеющиеся пакеты. SDK v1.1.0 не является новой версией MC. Снимок списка сохранён в `logs/twin/qualification_20261026/official_sdk_downloads.json`.
- [Официальное описание загрузок](https://x2-aimdk.agibot.com/en/dev/get_sdk/index.html) подтверждает отдельную поставку MC/sim extras.
- На [официальном GitHub AgibotTech/agibot_x2_urdf](https://github.com/AgibotTech/agibot_x2_urdf) есть актуальные модели, но releases пусты и бинарного MC в этом репозитории нет. XML X2 Ultra v1.3.0 скачан для сравнения (с hash и различиями в `upstream_model_diff.json`); более новая версия модели не была автоматически принята за модель .66. Там другой nominal pelvis inertia и ряд limits.
- Проверены публичные ресурсы AgibotTech и open.agibot.com. Найденный симулятор A2 относится к другому роботу и не использован как замена X2. Совместимый x86 MC v1.1.0-r9-rc9 **в проверенных публичных источниках не найден**; это не утверждение об отсутствии закрытой поставки у производителя.

Нужный запрос производителю: Linux x86_64 **SIM build MC v1.1.0-r9-rc9 (robot commit e3c738dc)** для lx2501_3_t2d5, совместимый с mc_param v1.1.0-r9-rc3 (be6171a9), плюс парный MuJoCo/HAL пакет и описание различий SIM/REAL, hashes и runtime dependencies. ARM64 пакет с робота не заменяет x86 build. Запрос не отправлялся.

## Проверки и следующий недостающий материал

11 целевых тестов прошли: геометрия груди/IMU, поворот через ±π, velocity window и clock reset, невидимый сектор, fixed-payload inertia, несовместимые body frames, независимость сравнения от мирового начала/heading, запрет сравнения разных команд, неизменность AMCL-параметров. Python — py_compile, shell — bash -n. Измерительные replay и полный Nav2 run выполнены в изоляции.

Для дальнейшего повышения достоверности нужны текущая per-unit calibration/URDF .66, полные raw bag trial05/06, одинаковые начальные позы и серии с внешней оценкой перемещения/поворота. Движения на роботе — только после отдельного объявления и подтверждения оператора. До этого разумно использовать новый профиль для проверки программной цепочки и записанные сенсоры для replay; оптимальные gains/ограничения движения по нему не выбирать.

## Дополнительно: настоящий FAST-LIO на сырых данных .66

Собран собственный x86 executable из имеющегося `candidates/fast_lio_portable/src/FAST_LIO`, включая QazBot patches времени/loopback. ARM install не изменялся. Сборка: `tools/twin/docker/build_lio.sh`, результат `runtime_x86/lio_ws/install`. Явно закреплён single-thread search path (`MP_EN` выключен, MP_PROC_NUM=1), соответствующий ARM-пути сборки; source-файлы для этого не редактируются. Логи и binary/config hashes сохранены.

`tools/twin/replay_raw_lio.py` публикует **только raw cloud и LiDAR IMU** на уникальные приватные темы каждого прогона, запускает настоящие FAST-LIO и production level_bridge. Записанные scan/odom/TF/AMCL не подаются алгоритму. До старта проверяются подписчики обоих новых процессов. Сохраняются исходные header и per-point timestamps, publisher pacing выбирается отдельно (1x или 0,5x для офлайн-проверки); это не тест производительности real time. MC API и publishers команд отсутствуют.

На `raw_comparison_input_01` подано 149 облаков и 2789 IMU. Получены 129–137 raw poses, 116–123 level poses, 54–63 скана в разных повторах. После 2 с прогрева сравнены 108–116 пар с одинаковыми source stamps, с одним начальным SE(3)-совмещением:

- Расхождение с **записанным FAST-LIO**, а не с физической истиной: position p95 2,1–2,2 см, полная orientation p95 0,09–0,10°.
- При текущем configured dense output конечных лучей ≈14,5%; при явном sparse output ≈9,65–9,72%, в исходной записи ≈9,51%. Это диагностическое согласование исторического режима публикации, не рекомендация менять текущую конфигурацию робота.
- Replay не побитово детерминирован: два одинаковых single-thread запуска имели 137 и 132 позы, на 132 общих stamps максимальное различие компоненты pose matrix ≈0,00683. Причины доставки/инициализации/таймингов не разделены, потерянные начальные кадры не замалчиваются. Свежий estimator не получает старую map history из записанного live-run.
- Оба процесса во всех завершённых опытах остановились code=0. `physically_validated=false` сохранён: это проверка воспроизведения локализации на записанных входах, **не** синтез LiDAR из MuJoCo и не подтверждение точности MC.

Результаты: `tests/integration_results/replay_raw_lio_twin*/{results.json,poses.npz}`; повторяемость — `logs/twin/qualification_20261026/raw_replay_repeatability.json`. Начальный диагностический запуск до добавления poses.npz содержит только results/logs.

Пример после сборки (в контейнере через env_container.sh):

```bash
source /workspace/control_backend/runtime_x86/lio_ws/install/local_setup.bash
python3 /workspace/control_backend/tools/twin/replay_raw_lio.py \
  /workspace/control_backend/logs/raw_comparison_input_01 UNIQUE_REPLAY_NAME \
  --publication sparse --rate .5
```

Финальная машинная сводка: `python3 tools/twin/write_fidelity_report.py logs/twin/qualification_20261026`. Она разделяет наблюдательный контракт, реальные replay и не прошедшую квалификацию физику; не повышает статус по одному удачному совпадению. .66 недоступен, оператор вне офиса; аппаратных действий и ожидания подтверждения движения сейчас нет.

Финальный контроль после изменений статуса: `observation_final_check.json`, 7/7 структурных проверок; публикационная задержка 48,7 мс, активные частоты odom≈9,52 Гц / scan≈4,75 Гц. Сохранён также текущий возраст источника (растёт при остановке входа), отдельно от возраста в момент публикации. В суммарном счётчике этого запуска 253 пропуска FK; стартовые и установившиеся пропуски пока не разделены счётчиками. Они не заполнялись позой таза. Этот контроль не доказывает отсутствие потерь/задержек при старте.

Финальный raw replay с уникальным namespace и явным discovery обоих новых estimator readers (`replay_raw_lio_twin_isolated`) обработал 137 поз, 116 пар для сравнения, smoke_passed=true, оба процесса code=0. До завершения остались только официальный MC и MuJoCo в исходной модели: body=1, fsm=4, STAND_DEFAULT, network=none. Тестовые observers, replayers и publishers скорости завершены.
