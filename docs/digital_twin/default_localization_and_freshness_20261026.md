Изменены локальные исходники `control_backend`. Установка на .66 и аппаратная проверка в этой задаче не выполнялись. Все ROS-проверки — в контейнере `qazbot-twin-sim`, network=none, domain=87, localhost; без команд реальному роботу.

## Обычный запуск без профиля

По запросу пользователя стандартное поведение теперь:

- `TrustConfig.admission_policy = go2`;
- `localization_trust_node.go2_nomotion_on_initialpose = true`;
- `tools/stack/stack_up.sh` и launcher официального twin выбирают Go2, если ничего не задано;
- после новой операторской позы Trust сам запрашивает обновление неподвижного AMCL; ручного `request_nomotion_update` не нужно;
- covariance, частицы, scan-score, якорь и коррекции map→odom остаются диагностикой; сохраняются свежесть критических данных, валидность и карта;
- strict сохранён как явный legacy-режим для регрессионного сравнения. Старые unit-тесты строгой политики теперь явно задают её, а тест default проверяет Go2;
- отдельный `go2_stationary_initialization.yaml` удалён как ненужный. Наблюдающий shadow явно отключает AMCL refresh, чтобы оставаться наблюдателем;
- `test_live_chain.py` в стандартном режиме использует настоящий AMCL и больше не делает ручных refresh-запросов в ветке Go2.

Сохранение/восстановление позы не включалось этим изменением; обычный dry-run bringup по-прежнему требует действительную initialpose. Допуски движения, скорости, MC, AMCL alpha и контроллер не менялись.

Проверка `go2_default_seed_01`: активная ветка запускает Trust **без params-file и без параметров политики/helper**. READY+MOTION_OK за 0,760 с, повторная поза за 0,840 с. Пропажа скана и неверная поза не открывают допуск. Настоящие AMCL и Trust, неподвижный fixture с задержкой source stamp скана 300 мс, никакого MC в тестовой цепочке. Девять проверок PASS.

108 unit/regression tests PASS: `test_go2_policy`, `test_ready_motion`, `test_source_failures`, `test_trust_gaps`, `test_seed_refresh`, `test_loc_trust`, `test_pose_persist`. Лог `logs/twin/go2_default_regression.log`. Python — py_compile; shell entrypoints — bash -n.

## Блокер 4: накопление старых входов в мосте

Обнаруженный механизм: `level_bridge` принимал Odometry с очередью 100 и облако с очередью 20, оба reliable. Если обработка медленнее входного потока, обработка старых входов может продолжаться после того, как уже пришли новые. Свежесть нужна по source stamp, поэтому это превращается в T1_stale; переписывать timestamps или увеличивать порог нельзя.

Изменение по умолчанию в `ws/src/lio/level_bridge.py`: обе подписки теперь `KEEP_LAST(depth=1), BEST_EFFORT`. Входные source stamps, точное сопоставление cloud/odom по времени, фильтры и выходной скан не менялись. Если соответствующая поза пропущена, скан не создаётся; старый скан не переименовывается в новый. IMU-очередь при определении уровня не менялась.

Это выбор последних сенсорных данных при перегрузке с допустимыми потерями. Это **не ускорение FAST-LIO** и не доказательство устранения всех аппаратных T1. Потеря нужной пары может уменьшить частоту скана; имеющиеся гейты свежести остаются обязательными. BEST_EFFORT-подписка совместима и с reliable-, и с best-effort-публикатором.

### Нагрузочная проверка настоящего моста и DDS

`tests/twin/test_level_bridge_backlog.py`: независимый ROS-производитель публикует Odometry/cloud 10 Гц; настоящий LevelBridge принудительно тратит 180 мс на cloud callback. Сравниваются прежние QoS и новые defaults; producer перезапускается между вариантами. По 8 с наблюдения. Level rotation зафиксирован в fixture, проверка не оценивает IMU-калибровку или геометрию FAST-LIO. Задержка 180 мс искусственная, не измеренная на роботе.

Прогон `level_latest_02`:

| Возраст скана p95 | 2,007 с | 0,460 с |

Повтор `level_latest_03`: p95 2,075 → 0,458 с, stale 84% → 0%; все проверки PASS. Номинальная проверка без принудительной задержки `level_latest_nominal_01`: по 75 сканов в обоих вариантах, p95 4,4 / 4,9 мс, stale=0; все проверки PASS.

Все четыре проверки нагрузочной пробы PASS, source stamps строго возрастают и совпадают с исходными timestamp обработанных облаков. Возраст измеряется внешним подписчиком; он также делит executor с принудительно медленным мостом, поэтому включает ожидание callback observer, а не только транспорт/вычисление.

Предварительный `level_latest_01` показал, что одного depth=1 при reliable недостаточно: p95 всё ещё 1,535 с. Тот тест также не перезапускал producer между вариантами, поэтому вклад очереди и сохранившегося состояния DDS отдельно им не измерен. Нельзя приписывать весь выигрыш только BEST_EFFORT; конечная проверка оценивает полный вариант с корректно раздельными producer.

Результаты — `tests/integration_results/level_latest_*/results.json`. Порог Trust 0,5 с сохранён. Это устранённый программный механизм накопления, а **не закрытие всего блокера №4**. Для .66 ещё требуется измерить raw→FAST-LIO→bridge→Trust при её обычной нагрузке.

## Что проверено по блокеру 5

`tests/twin/test_ghost_obstacle.py`, финальный `ghost_voxel_04`: два настоящих Nav2 controller_server с их встроенными costmap; целей нет, адаптер/MC не участвуют. Сравниваются стандартный ObstacleLayer с 2D scan и стандартный VoxelLayer с явно заданными 3D hit/ray observations.

Контролируемая сцена: объект в (1,2; 0; −0,5) относительно сенсора; после удаления появляется реальное отражение пола в (2,4; 0; −1,0) на том же 3D-луче. В 2D height slice этот floor return исключён, поэтому остаётся inf без доказательства свободного пространства.

- Оба слоя отмечают присутствующий объект: cost=100.
- Если направление объекта не наблюдается, оба сохраняют объект: cost=100.
- Присутствующий объект не очищается.
- После настоящего свободного 3D-луча VoxelLayer очищает ячейки: cost=0; прежний 2D слой сохраняет ghost: cost=100.

Четыре lifecycle-проверки и четыре проверки поведения PASS. ROI для измерения — 3×3 ячейки вокруг прежнего объекта: одиночная точка лежит у границы ячеек, точный float индекс не является устойчивым измерителем. Это исправило ошибку измерения раннего `ghost_voxel_03`; первые два запуска проверяли неподходящие способы запуска costmap и не являются измерениями поведения.

**Производственная costmap не переключалась на 3D.** Для переноса нужны корректно выраженные облака, точка начала лучей, вертикальная сетка и проверка на реальных записях; синтетическая сцена этого не подтверждает. Автоматическое стирание всех inf/ненаблюдаемых секторов не включалось. Блокер №5 остаётся открытым, но безопасный принцип решения проверен независимо от MC 1.0.0.
