# Архитектура и принятые решения

## Слои и границы
| Слой | Что | Где | Правится ли |
|---|---|---|---|
| Навигационный стек | Nav2, AMCL, Trust, Coordinator, RPP, Motion Adapter | `control_backend/ws/src/{navigation,lio,maps}` | только в основном репозитории; twin его не копирует |
| Plant-пакет | замена FAST-LIO + level_bridge: odom/TF/scan из симулированного тела | `ws/src/x2_twin_sim` | да |
| Bring-up | запуск стека «как на роботе» (`stack_up.sh`, `run_*.sh`) | `ws/src/x2_twin_bringup` | да |
| Сценарии | клиент оператора + аналитика | `ws/src/x2_twin_scenarios` | да |
| Симулятор | официальный mc + MuJoCo | `vendor/` (монтируется) | нет |

Граница «аппаратура»: ровно два интерфейса — **сенсорные топики** (`/qazbot_lio/*`, `/qazbot_d1_map/tf`) и **интерфейс MC** (`/aima/mc/*`,
`/aimdk_5Fmsgs/srv/*`). Стек видит их так же, как на роботе, поэтому не знает о симуляции.

## Решения и причины
1. **Два контейнера (sim, stack), а не один.** Один процесс — одна ответственность; AgiBot-бинарники не попадают в образ стека; стек
   пересобирается независимо от sim. Сеть `twin` — `internal: true`: нет маршрута ни в LAN (где физический X2), ни в интернет.
2. **Бинарники AgiBot монтируются, не запекаются.** Лицензионная гигиена (образы можно публиковать без них) и меньший образ. `sim-init`
   копирует их в именованные тома (mc/sim пишут кэш и логи рядом с собой), повторно — только при смене содержимого.
3. **Production-имена топиков.** Plant публикует те же `/qazbot_lio/scan`, `/qazbot_lio/odom_level`, `/qazbot_d1_map/tf` с теми же
   частотами/QoS — стек запускается без ремапов; `test_amcl_parity` защищает параметры AMCL/map_server от расхождения с боевым launch.
4. **Сценарий — клиент, а не оркестратор процессов.** Стек поднимает `twin.launch.py` (как на роботе), сценарий подключается узлом ROS
   и действует как оператор: RViz-поза → no-motion обновления → baseline → `confirm_anchor` → явная регистрация → цели.
5. **Исходы целей — измерения (мягкие проверки).** Официальный MC перелетает и срывает разворот на месте (Блокеры 1–2); сценарий
   записывает это, а жёстко проверяет только инварианты (изоляция, лимиты, регистрация, отсутствие глобального `/cmd_vel`).
6. **Fast DDS только UDP в контейнере стека.** SHM не пересекает IPC-пространства контейнеров; UDP по внутренней сети — поддерживаемый путь.
7. **`init: true` у sim.** Официальный `start_sim.sh` считает зомби-процессы «запущенным экземпляром»; tini их подбирает.
8. **Образы**: digest-pin базы (`ros:humble-ros-base`, 758 МБ вместо `desktop-full` 3,9 ГБ), rosdep из `package.xml`, установка без
   рекомендованных пакетов, `opencv-python-headless` вместо `python3-opencv` (VTK/LLVM ~400 МБ), тяжёлые вендорные сборки кэшируются
   отдельным слоем (правка кода twin не пересобирает Smac и aimdk_msgs), BuildKit cache mounts для apt, whitelist `.dockerignore`
   (контекст — каталог с гигабайтами логов).
9. **Патченый Smac в образе.** Боевой `nav_full.launch.py` не стартует без него (проверяет sha256); собирается на закреплённом коммите
   navigation2 1.1.20 с `candidates/nav2_smac_bounds/bounds.patch`, манифест генерируется при сборке.

## Мир со стенами
`x2_twin_sim/world.py` (чистый модуль, без ROS) строит копию официальной конфигурации робота, где `scene.xml` дополнен боксами по прогонам занятых
клеток карты; все остальные вендорные файлы — символьные ссылки, вендорское дерево не меняется. Проверки: точное покрытие (никакая клетка не
пропущена и не посчитана дважды), спавн свободен с зазором ≥ 0,52 м, преобразование «карта → мир sim» записано в `manifest.json`. Супервизор sim
генерирует мир при старте контейнера и запускает `start_sim.sh -c <dir>` (**не** `-s` вместе с `-c`: вендорский скрипт тогда стирает выбранную
конфигурацию), затем проверяет, что процесс `aima-sim-app` действительно использует сгенерированный `default.yaml`.
Измерено для карты `first_map_nav2_v2`: 4708 занятых клеток → 1997 боксов, зазор спавна 0,91 м. Первичная валидация геометрии лучами MuJoCo против
точных пересечений клеток (360 лучей, 0 несовпадений, максимум 4,9e-15 м) выполнена параллельным сеансом на карте v3
(`control_backend/docs/digital_twin/interactive_rviz_20261026.md`); для этого проекта проверены покрытие и преобразование (юнит-тесты) и факт
использования мира процессом sim.

## Оптимизации (измерено 26.10.2026, хост 12 ядер / 62 ГБ)
| Что | До | После |
|---|---|---|
| Образ стека | 2,35 ГБ (rosdep с рекомендованными пакетами, `python3-opencv` → VTK/LLVM, компиляторы и `-dev`) | **1,76 ГБ** (`--no-install-recommends`, `opencv-python-headless==4.7.0.72`) |
| Образ sim | 4,05 ГБ (`osrf/ros:humble-desktop-full`) | **1,79 ГБ** (`ros:humble-ros-base` по digest + только нужные библиотеки) |
| Пропуски real-time MC («worker missed wakeup») при headless-рендере | 6274 в минуту | **738 в минуту** (`LP_NUM_THREADS=1`, framebuffer 640×360) |
| `cap_add: SYS_NICE` / `ulimits rtprio` | – | проверены A/B, эффекта нет (не root) → удалены |
| Пересборка при правке кода twin | ~8 мин (пересборка Smac и aimdk_msgs) | ~40 с (тяжёлые вендорные пакеты в отдельном кэшируемом слое) |
| Холодный старт `make up` (тома пусты, `sim-init` копирует бинарники) | – | **59 с** (sim healthy ~45 с, стек +15–20 с) |
| `make test` (flake8 + 30 тестов в контейнере) | – | ~40 с при тёплом кэше |
| Лёгкий режим (`lite-up` + сценарий) | – | ~35 с |

Диск: образы + кэш BuildKit занимают много (сборка требует ~10 ГБ свободного); `docker builder prune` безопасно очищает кэш.
