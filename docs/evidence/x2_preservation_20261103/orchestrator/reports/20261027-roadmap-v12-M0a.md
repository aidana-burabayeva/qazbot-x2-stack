## What was implemented (design §3.4–3.6, step 1 only)
- **New node `ws/src/lio/native_odom_bridge.py`** (`qazbot_native_odom_bridge`). Reuses the pure math in
  `native_odom.py` unchanged (SourceGuard/JumpGuard, Twist0p3, Decimator, cov_planar, imu_footprint_yaw).
  - Input: `/aima/mc/leg_odometry` (sensor QoS).
  - Output: TF odom→base_footprint (x, y, yaw only), `/qazbot_native/odom` (odom/base_footprint, z = IMU z,
    0.3 s twist in base_footprint axes, leg pose covariance diagonal, twist covariance = nominal 1e-3) and
    `/qazbot_native/status` (JSON, 1 Hz).
  - Stamp = the leg sample's source stamp, never re-stamped. Decimated to `publish_rate_hz`, default **30**
    (allowed 10–100).
  - Guards: foreign frame → drop. Non-finite or non-unit quaternion → LATCH. Origin jump (>0.05 m + 1.5 m/s·dt or
    >0.3 rad) → LATCH. Stamp >0.2 s in the future → drop. Age >0.2 s when due → withheld. Stamp went back → twist
    baseline cleared.
  - Any guard stops all output, so trust goes T1_odom_stale (fail-closed).
  - `mode` accepts only `native_imu`; `native_base` is refused.
- **`level_bridge.py`**: new param `publish_tf` (default true).
  - With `publish_tf:=false` it creates **no TF publisher at all**. `/qazbot_lio/odom_level` and `/qazbot_lio/scan`
    stay byte-identical (tested: message equality against true).
  - Scan consistency, verified from the code: `on_cloud` takes `cloud_registered` (LIO world) and transforms it with
    R_lv and the **LIO pose at the same cloud stamp** (`Q = R_lv·P − p_lv`, then rotation by −yaw_LIO). LIO drift
    cancels, so the scan is the levelled body scan in base_footprint (IMU footprint, LiDAR-forward yaw). That is the
    same physical frame the native bridge publishes, so AMCL's cached laser pose and trust's frame check stay valid.
    LIO is still needed for the scan.
- **`localization.launch.py`**: new args `odom_source:=lio|native_imu` (choices, default lio), `native_rate_hz`
  (30.0) and `native_leg_topic` (default `/aima/mc/leg_odometry`, used only by tests).
  - Level_bridge gets `publish_tf:=true|false` through a substitution that refuses any other source.
  - The native bridge is conditional on native_imu, has a shutdown guard, and is the last staggered process, so
    lio-mode start times are unchanged.
- **`localization_trust_node.py`**: params `odom_topic` (default `/qazbot_lio/odom_level`, the previous hard-coded
  value) and `odom_source` (informational).
  - Both appear in the start log line and in `~/status`.
  - A warning is logged if source=native_imu while still on the LIO topic.
  - No checks, thresholds or policy changed.
- **`run_nav_full.sh`**: `odom_topic:=${QAZBOT_ODOM_TOPIC:-/qazbot_lio/odom_level}`.
- **`tools/stack/stack_up.sh`**: `QAZBOT_ODOM_SOURCE` (lio default | native_imu, anything else exits 2).
  - Passed to localization (`odom_source`), trust (`odom_source`, `odom_topic`) and Nav2 (`QAZBOT_ODOM_TOPIC`).
  - In native mode it waits for the "native_odom_bridge started" log line.
  - It prints the mode.
- **`stack_down.sh`**: native_odom_bridge added to the leftover-process pattern.
- **`check.sh`** runs the new `tools/stack/odom_owner_probe.py` (read-only), which checks two things:
  - graph: exactly one of level_bridge or native bridge publishes `/qazbot_d1_map/tf`;
  - data: every odom→base_footprint TF sample equals the owner's odometry message.
  - `check.sh` also adds `/qazbot_native/odom` to the age probe. `graph_probe.py` lists the native topics.
- Not done (out of M0a scope): the `odom_compare` launch arg (the standalone `native_odom_compare.py` already
  exists), T1_lio_stale (that would be a trust policy change), the trust `odom_src` deque (at 30 Hz the cost is
  about 120 entries per message, negligible), and the docs (QUICKSTART, DECISIONS).

## Risks / open items
1. **AMCL alphas with native odom.** AMCL defaults are unchanged (OmniMotionModel, alpha 0.2, update_min_d/a
   default).
   - Native odom has no LIO drift during turns, but leg-odometry drift on straight walks and on slippery floors is
     NOT measured (trial06 is rotation only).
   - Do not lower the alphas or change T5 (0.10 m / 0.10 rad) until a passive compare run (native_odom_compare.py)
     on walks.
   - During in-place turns the IMU footprint really moves about 0.115 m (lever arm). This is consistent with the
     scan frame, but AMCL sees it as translation.
2. **leg_odom origin reset on MC restart.**
   - A reset with continuous stamps → JumpGuard LATCH → the bridge stops for good → trust stale. Recovery is a
     localization relaunch plus a new pose and anchor.
   - **Gap:** the jump bound grows with the stamp gap (0.05 m + 1.5 m/s·dt). A reset after a long stream gap
     (e.g. 3 s gap → 4.55 m allowed) is NOT latched. During the gap trust goes stale. Afterwards AMCL sees a
     teleport, which T5 (map→odom step > 0.10 m) should catch, but that is unproven.
   - Recommendation: cap dt in the bound (e.g. ≤ max_age), or latch on any gap > max_age combined with a jump
     > JUMP_M. Not changed here because the guard values come from the design. Needs a decision.
   - Also: the leg_odom origin moved 0.53 m between snapshots for an unknown reason (design §4.4).
3. In native mode, T1_odom_stale no longer covers LIO death. LIO failure is caught only by T1_scan_stale. A frozen
   LIO pose with the cloud still flowing produces a fresh scan (the same risk as today). T1_lio_stale was not added
   because it would be a policy change.
4. Trust `_moving` (0.02 m/s over 0.6 s) now runs on the native footprint at 30 Hz. Standstill sway has not been
   measured; a false "moving" affects only the AMCL-overdue logic. Measure it in compare mode first.
5. In native mode, `/qazbot_lio/odom_level` still says frame `odom` but it is LIO's origin, not the TF odom. All
   switched consumers are fine: trust via odom_topic, Nav2 via QAZBOT_ODOM_TOPIC. `nav_plan.launch.py` still
   hard-codes `/qazbot_lio/odom_level` (planning-only launch, twist only); it is not used by stack_up.
6. Clock: if the PTP between MC and the host breaks, the future/stale guards stop publication. This is fail-closed,
   but it takes the whole stack out of READY.
7. Pre-existing loc_trust suite breakage (see Tests) and the unexplained 16:16 overwrite in ws/src/navigation
   (design §4.1) remain open.

## Addendum: item 8 fixed (coordinator decision): origin reset after a long stream gap is now fail-closed
- **Choice: cap dt in the jump bound.** I did not pick "new session after every gap". Cap and resume is simpler: one
  line in `JumpGuard`, no new state. It is also the safer of the two:
  - every inconsistent pose after a gap latches;
  - the stream resumes only when the new pose agrees with the last one within the capped bound;
  - the "new session" alternative would latch permanently on every harmless DDS stall over 0.2 s while the robot
    stands.
- **New bound:** `|dp| > JUMP_M + JUMP_M_PER_S·clamp(dt, 0, JUMP_MAX_DT)` with `JUMP_MAX_DT = NATIVE_MAX_AGE =
  0.2 s`, so the bound never exceeds 0.35 m. The yaw bound of 0.3 rad was already independent of dt.
- **Why 0.2 s:**
  - Leg odometry runs at 139–168 Hz; trial06 stamp gaps are p50 6 ms, max 14 ms. The cap is 14× the largest real
    gap.
  - A gap over 0.2 s already means the stream was stale and output was paused.
  - 0.35 m covers more than 1 s at the Nav2 limit `max_linear` 0.3 m/s, and more than 1.4 s at the fastest trial06
    footprint speed of 0.24 m/s.
  - The 1.5 m/s rate is still 5× the Nav2 limit for normal sample-to-sample motion.
- **Behaviour after the fix:**
  - MC restart with a 3 s gap and a 1.5 m origin shift → `origin_reset:dp=1.552m,gap=3.0xxs` LATCH. No TF or odom
    until relaunch, and `/qazbot_native/status` shows the reason.
  - Before the fix the bound in that case was 4.55 m, so the reset passed silently.
  - A gap with the pose within 0.35 m → publication resumes and the twist baseline refills.
- **Known cost:** if the stream stalls while the robot really walks more than 0.35 m (implausible, because MC
  publishes leg odometry while it walks), the bridge latches. That is fail-closed and needs a relaunch.
- **Edited (backups `*.bak_20261027_pre_m0a_gap`):** `ws/src/lio/native_odom.py` (JUMP_MAX_DT + JumpGuard).
  `native_odom_bridge.py` got a backup but did not need any change. The compare node shares the guard and gets the
  same behaviour.
- **New tests in `tests/lio/test_native_odom_bridge.py`:**
  - node: 3 s gap + 1.5 m reset → latched with gap in the reason and in status; 3 s gap + 0.4 m → latched; 3 s gap
    with dx 0 or 0.3 m → resumes (TF and odom published, no latch);
  - pure: bound table (gaps 0.006 / 0.1 / 0.2 / 3 / 30 / −5 s around the 0.35 m and 0.05 m edges), cap
