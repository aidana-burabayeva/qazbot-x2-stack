## 2. (a) Code-level filter analysis — root cause of D-07
- Symptom: low objects are not marked in the local costmap.
- Proximate cause: `level_bridge.py:235` (same in the C++ projector) removes every return below 0.33–0.43 m above the floor.
- Root cause: the band floor was set as a fixed IMU-relative slice with a margin that grows with range, "~2 deg of sway"
  (comment `:43-46`).
  - It assumes levelling errors of a few degrees in the FAST-LIO world frame.
  - It is not referenced to the measured floor.
- Result: any object below ~0.35 m (0.6–1 m) to 0.43 m (3 m) is filtered by design, whatever the sensor sees.
- Is "band floor rises with r" justified by the measured data?
  - Static: NO.
    - The per-frame floor residual does NOT grow with range: sd 1.36 cm @0.45–0.6, 1.11 @0.8–1.0, 0.81 @1.25–1.5, 0.66 cm @1.5–2.0.
    - p99.9 is 4.4 / 3.5 / 2.7 / 2.2 / 1.8 / 2.0 cm for the bins 0.45 / 0.6 / 0.8 / 1.0 / 1.25 / 1.5 m.
    - Near-range bias is +1.2 cm at 0.45–0.6 m and +0.5 cm at 0.6–0.8 m.
    - Static tilt variation is tiny: pitch p1–p99 −0.13..−0.05°, roll −0.22..−0.06°, angle to the global plane p99 0.24°.
  - A range-proportional margin would be justified only by an angular levelling error. That error is NOT MEASURED here (no walking data).
  - Data that could measure it: logs/manual_amcl_walk_02 (100 s), manual_amcl_turn_01 and manual_amcl_reverse_01 contain the raw
    cloud plus LIO odometry. NOT CHECKED.
- 0.329 m constant offset: no measured reason found. The floor noise is ~1–4 cm, so 0.33 m is ~8–30× the noise.
  It looks like a slice choice for 2D SLAM scans rather than a floor-noise margin. HYPOTHESIS: the original purpose was keeping
  floor fans out of the slam_toolbox /scan.

## 5. Candidate filter (analysis only, NOT deployed, no code written)
- **Low-obstacle band relative to the measured floor plane**, instead of the IMU-relative z > −0.65 + 0.035 r.
  1. Per scan, fit the floor plane in the deskewed cloud (robust: RANSAC/SVD on points near the predicted floor, 0.45–3 m),
     using the LIO-levelled prediction as the seed. Reject the fit if inliers are < N_min or the tilt jumps by more than X° vs the
     previous scan; then fall back to the current band.
  2. Mark a point if h_plane > T_low, with T_low = 0.07 m (static evidence supports 0.05) and h < Z_MAX.
     Require ≥3 returns per 5 cm cell (≈1 after decimation, or keep raw-cloud input) or 2-scan persistence.
  3. Keep the range-proportional term only if the walking data show residual tilt error: margin = k·σ_tilt·r, with σ_tilt
     measured from walk_02 / turn_01 / reverse_01.
  4. Clearing rays must use the same floor-relative band (consistent with the D-04 candidate C).
  5. Feed a separate observation source (e.g. a `scan_obstacles_low` PointCloud2 into the existing obstacle_layer, marking
     only), so slam_toolbox /scan keeps its slice.
- Reuse-first: Nav2 already accepts PointCloud2 observation sources with min/max_obstacle_height.
  - However, that height is relative to the costmap frame, not to the floor plane. A plain ObstacleLayer/VoxelLayer on the levelled
    cloud with min_obstacle_height 0.07 is equivalent only if the levelling error stays below ~T/r (0.07/2 m ≈ 2°).
    Walking data must decide between this and plane-relative filtering.
  - The FAST-LIO `point_filter_num: 3` decimation reduces low-object returns 3×. Consider feeding the raw `lidar_pointcloud`,
    deskewed or not, to the low-obstacle source. Costs CPU; NOT CHECKED.
- Henki: if implemented, it should be a new single-responsibility C++ node (or a qazbot_lidar_projector option) with params in

## 7. Q5 C++ projector: 3/3579 missing scans — mechanism found (offline, no rerun)
Facts:
- `src/lidar_projector_node.cpp:160-171` does the following in order:
  1. Counts the cloud (`++n_cloud_`, scan_every 2).
  2. Looks up the pose with the EXACT stamp `tracker_.find(key)`.
  3. If the odometry for that stamp has not arrived yet, it returns silently. There is no log, no wait and no retry.
- The Python candidate has the same logic.
- In the bag, `/qazbot_lio/odometry` was recorded AFTER the matching `/qazbot_lio/cloud_registered` for 52/7194 stamps (0.72 %);
  17 of them are on the processed parity. `order.py` and `order.pkl` hold this check.
- Missing-scan stamps:
  - All three C++-only missing stamps (1793701951310885906, …2201910807847, …2367310158967) are among those 17.
    Odom arrived 0.047 / 0.086 / 0.042 ms after the cloud.
  - The shared C+++Py gap (…2280310693025) is also among them (odom +0.046 ms).
  - Of the 17 stamps, C++ dropped 4 and Python dropped 1. Among the 3559 other processed stamps, 0 were dropped by either.
- ros2 bag play republishes in recorded order. The faster C++ callback runs the cloud before the odom sample is taken; the slower
  Python callback usually finds it.
- Cause class:
  - Inter-topic delivery order race combined with exact-stamp lookup without a buffer.
  - Not QoS loss, not executor starvation and not CPU: latency p99 7.9 ms, and the single run had 0 loss.
  - The same race can occur live: the live recorder itself saw odom after cloud in 0.7 % of cases. Live impact: an occasional
    missing 5 Hz scan (0.4 s gap).
- Fix direction (not implemented):
  - Keep up to 1–2 pending clouds and process each when its odom arrives (or within ~20 ms), or use a message_filters
    ExactTime/ApproximateTime synchronizer.
  - Add a throttled WARN/DEBUG counter for "cloud without pose".
- Confirmation command (domain 76, optional): replay only those 4 stamps' neighbourhood with odom delayed or advanced and check
  1:1 output; or add a count of pose misses in a test build.
